## Відкриті проблеми

### 76. Часові мітки залежать від часового поясу PostgreSQL

**Спостереження.** Колонки користувача `email_verified_at`, `created_at` і `updated_at` у схемі оголошені через `timestamp(...)` без `withTimezone: true` ([`schema.ts`](../../packages/backend/src/database/schema.ts#L60), [`schema.ts`](../../packages/backend/src/database/schema.ts#L69)). Це узгоджується з описаним у вихідному issue ризиком різної інтерпретації часу, записаного через `now()` і через JS `Date`.

**Висновок.** Зміна типу колонки на `timestamptz` або явне встановлення UTC для кожного з'єднання в цій схемі не підтверджені. Потрібно також перевірити перетворення дат у відповідях login/init: цей аудит не простежував їхній повний шлях.

### 77. `token` обов'язковий у схемі входу

**Спостереження.** `LegacyLoginInputSchema` та `IdentifierLoginInputSchema` обидві оголошують обов'язковий `token` ([`login.ts`](../../packages/shared/src/schemas/auth/login.ts#L3), [`login.ts`](../../packages/shared/src/schemas/auth/login.ts#L10)).

**Висновок.** Сценарій входу без поля не приймається цими схемами. У цьому аудиті призначення `token` у сервісі входу не простежувалося, отже невикористання поля залишається твердженням вихідного issue, а не незалежно підтвердженим висновком.

### 79. HTTP `admin_guard` не повертає канонічну помилку

**Спостереження.** Для відсутнього користувача й користувача без ролі admin middleware встановлює HTTP 403 і payload `{ status: 'forbidden', message: 'Admin access required' }` ([`admin-guard.ts`](../../packages/backend/src/app/middlewares/admin-guard.ts#L8)).

**Висновок.** Цей payload не відповідає канонічній формі `status: 'error'` з `code`, описаній у [`error-response.ts`](../../packages/shared/src/responses/error-response.ts). У коді WS-guard уже використовує перетворення `forbidden()` до application error payload, але це не виправляє окремий HTTP middleware.

## Пункти, де початковий документ застарів

### 55. Зберігання тексту `final_prompt`

Вихідний документ позначає пункт як відкладений. У поточному коді є `purge-llm-prompts.ts`, який видаляє текст промптів, зберігаючи SHA-256 та довжину; за замовчуванням видаляє весь збережений текст, а при opt-in retention — старіший за налаштований термін ([`purge-llm-prompts.ts`](../../packages/backend/src/scripts/purge-llm-prompts.ts#L8)). `feature_list.json` пов'язує цю роботу з feat-065. Отже, статус у старому issue-документі слід оновити з «відкладено» на виправлений пізнішою роботою.

### 74. Контракти спільних відповідей

`InitResponse` більше не є окремим вручну написаним інтерфейсом: він виводиться як `WithCanonicalError<typeof InitResponseSchema.infer>` ([`main-controller.ts`](../../packages/shared/src/responses/main-controller.ts#L20)). Це виправляє наведений у issue приклад розходження між схемою і типом `InitResponse`. Аудит не встановлював, чи усунуті всі інші прогалини пункту (типи push-підписок та runtime-перевірка відповідей).

### 75. OAuth без конфігурації

Сервіс перевіряє наявність `clientId`, `clientSecret` і `redirectUri` перед використанням провайдера ([`oauth-service.ts`](../../packages/backend/src/app/services/auth/oauth-service.ts#L31)). Контролер має endpoint налаштованих провайдерів (`GET /auth/oauth/providers`) і повертає їх фронтенду ([`oauth-controller.ts`](../../packages/backend/src/app/controllers/http/auth/oauth-controller.ts#L38), [`http-routes.ts`](../../packages/backend/src/app/routes/http-routes.ts#L230)). `SocialAuthButtons.vue` бере цей список і створює кнопки лише для налаштованих провайдерів ([`SocialAuthButtons.vue`](../../packages/frontend/src/components/SocialAuthButtons.vue#L8)). Це закриває обидві пропозиції вихідного issue на рівні реалізації. Поведінкові тести в цьому аудиті не запускалися.

### 80. Шлях імпорту в туторіалі

У прикладах документації repository імпортується через `#app/repositories/index.js`, наприклад у [`services.md`](../../documentation/backend/services.md#L56). Це відповідає правилу barrel із вихідного issue. Повний прогін backend-тестів у цьому аудиті не повторювався.

## Межі перевірки

- Перевірено поточний код у робочій гілці, а не кожен історичний PR або кожен пункт 1–80.
- Тести, typecheck і документаційна збірка не запускалися; твердження про виправлення підтверджені читанням реалізації та наявної документації.
- Для пункту 74 повний аудит контрактів вимагатиме окремої перевірки всіх response schemas, клієнтських типів і runtime-шляху серіалізації.
