### Деталі середніх

**M1.** Шлях повідомлення в `onMessage` (`ws-handlers.ts:254`):

- `ping` → `pong`, оновлення токена в Redis без очікування, вихід. PostgreSQL не зачіпається.
- Невалідний JSON або повідомлення, що не пройшло схему → оновлення токена в Redis, помилка, вихід.
  PostgreSQL не зачіпається.
- Валідне повідомлення (подія може бути невідомою) → оновлення токена в Redis, далі
  `wsSessionHandler`: читання сесії з Redis і запит `users.session_token` через пул перевірки сесій
  (`database/session-check-db.ts:29`, `SESSION_CHECK_POOL_MAX = 5`). Лише після цього диспетчер
  шукає маршрут і перевіряє ліміт (`vendor/utils/routing/ws-api-dispatcher.ts:54`); для невідомої
  події ліміту немає.

`onMessage` асинхронний і не очікується uWS, тож обробники накопичуються. HTTP має бюджет L1
(600/хв на IP), WS-еквівалента немає: ліміт на upgrade обмежує лише нові з'єднання. Вплив під
навантаженням не вимірювався. Для виправлення оцінити два заходи: ранній загальний ліміт
повідомлень на з'єднання (до Redis і PostgreSQL) та обмеження кількості одночасних обробників на
сокет.

**M2.** `upsertSubscription` → `updateByEndpoint` (`push-subscription-repository.ts:173`) змінює
`userId` рядка без зміни id. Сусідній `getLogsBySubscriptionId` фільтрує за `userId`, тож ці два
методи розійшлися з наміром. Тестів журналу після переходу підписки немає. Виправлення має
перевірити всі способи читання: список підписок із журналами, окремий журнал і статистику.

**M3.** Суперечить feat-065, де текст промптів зберігається лише з `AI_USAGE_STORE_PROMPTS=true`.
Той самий клас, менший вплив: `push-notification-sender-service.ts:194` логує `WebPushError` з
`endpoint`, `headers`, `body`.

**M4.** `user-online-repository.ts:94` обрізає `limit` до 100, тому `rows.length > limit` при
`limit=100` завжди хибне. Менші значення працюють. Тестів на цей сервіс немає.

**M5.** Довжини колонок: `packages/backend/src/database/schema.ts:128-147`. Обробляється лише
SQLSTATE `23505`; `22001` не обробляється ніде. Те саме в `update-subscription.ts:3-13`.

**M6.** `packages/frontend/src/utils/api-path.ts:8` читає `VITE_API_PATH_PREFIX` під час збірки.
Сценарій описано в `documentation/en/backend/deployment.md:95-119` як робочий. Те саме під
`pnpm app:up`, коли `packages/backend/.env` задає `API_PATH_PREFIX`.

**M8.** vueuse 15.0.0 викликає `onDisconnected` і для явного `close()`. `resolveWebSocketCloseAction`
повертає `reconnect` або `refresh-token` для кожного коду поза 4xxx. `websocket-close.spec.ts`
покриває лише чисту функцію.

**M9.** `push.spec.ts:83` закріплює ранній вихід тестом. Другий сценарій: `pushManager.subscribe`
вдався, а `POST push-subscriptions` ні — повторна спроба повідомляє про успіх без запису на сервері.

**M10.** Перенаправлення працює лише коли `/login?redirect=…` відкриває користувач із наявною
сесією. Вхід через OAuth також його губить.

### Критерії завершення

Усі сценарії нижче покрито тестами (2026-11-11): `e2e-live/push-account-switch.spec.ts` (A → вихід → B, повторна синхронізація), `useWebSocketConnection.spec.ts` (старий сокет), `SupportView.spec.ts` (відновлення чату), `admin-pagination.pg.test.ts` (99 / 100 / 101), негативні перевірки типів у `define-route.spec.ts` і `api-client.spec.ts` (контракти).

Кожен сценарій — тест, що падає до виправлення.

- **M2 + M9.** A → вихід → B в одному браузері: B не отримує push користувача A і не бачить його
  журналів чи статистики.
- **M9.** Підписку створено браузером, але `POST push-subscriptions` завершився помилкою: повторна
  спроба справді синхронізує сервер.
- **M8.** Старий сокет закривається після відкриття нового: запити нового лишаються активними,
  перепідключення не планується.
- **M11.** Чат втрачає з'єднання після прийняття повідомлення: інтерфейс відновлюється, повідомлення
  не дублюється.
- **M4.** Пагінація працює на межах 99 / 100 / 101 запис.
- **Контракти.** Неправильний метод, body або params контракту спричиняють помилку компіляції.

## Рекомендація: автоматична перевірка відповідності API фронтенда й бекенда

**Суть:** винести контракт маршруту в `packages/shared` і будувати на ньому і маршрут бекенду, і
виклик фронтенду. Розбіжність стає помилкою `pnpm typecheck`, яку вже ловить CI, без кодогенерації
й нових інструментів.

### Поточний стан

- Бекенд уже зв'язаний зі схемами: `defineRoute` бере `validator` і `ResponseSchema` із `shared`, а
  відповідь перевіряється під час виконання.
- Фронтенд бере з `shared` лише типи (`import type` у `packages/frontend/src/utils/api.ts:5`), а
  шлях, метод і тип відповіді з'єднує вручну: `baseApi.http<T>('GET', apiPath('push-subscriptions'))`.
  Ніщо не перевіряє, що цей `T` належить саме цьому маршруту.
- Наслідок уже є: локальний `PushSubscriptionResponse` у `packages/frontend/src/utils/api.ts:265`
  не відповідає реальній відповіді, і компілятор цього не бачить.
- `validator` на маршруті необов'язковий, тож маршрут із тілом може не мати схеми запиту.

### Рішення дизайну, які треба зафіксувати перед пілотом

Перша редакція пропонувала передавати фронтенду об'єкт контракту зі схемами і водночас не тягнути
схеми в бандл. Це суперечність: runtime-імпорт такого об'єкта створює залежність від
ArkType-схем, і покладатися на їх видалення збирачем не можна.

1. **Межа пакетів.** Браузеру — метод, шлях і типи (значення без схем, типи через `import type`).
   Серверу — окрема прив'язка схем до контракту. Схеми не потрапляють у бандл фронтенду.
2. **Вхідний і вихідний тип.** Дані, які надсилає клієнт, можуть відрізнятися від результату
   серверної валідації через parsing, defaults і morphs. Простого `schema.infer` недостатньо:
   клієнт типізується вхідним типом схеми, обробник — вихідним.
3. **Повна форма виклику.** `params`, `query`, `body`, `signal` і наявні клієнтські опції. Новий
   клієнт використовує поточний транспорт із його CSRF і перевіркою зміни акаунта
   (`packages/frontend/src/utils/base-api.ts:369`), а не замінює його.
4. **Серверні політики.** Middleware, guards, ліміти запитів і ліміти тіла лишаються конфігурацією
   бекенду і в контракт не входять.
5. **Побудова URL.** Крім типізації шляхів потрібні фактичне кодування параметрів шляху та
   серіалізація query.

### Кроки

| Крок | Що робимо                                                                                                                                                    | Розмір          |

**Пілот (C1–C3 + C5a)** охоплює три різні маршрути: групу `push-subscriptions` (де дрейф уже є),
один маршрут із query і один маршрут автентифікації. Масова міграція (C4) починається лише після
перевірки на цих трьох.

### Відхилені варіанти

- **OpenAPI + генерація клієнта.** Другий формат поруч з ArkType і крок генерації, який треба
  тримати свіжим. Має сенс лише за появи зовнішніх споживачів API.
- **Перевірка відповідей на фронтенді під час виконання.** Тягне ArkType і схеми в бандл та дублює
  те, що бекенд уже робить. Максимум — увімкнути в e2e.
- **Лише e2e-тести.** Ловлять розбіжність тільки на покритих сценаріях і пізно.

### Обмеження

- Типи гарантують форму даних, а не поведінку: дрейф на кшталт загубленого `?redirect=` (M10) вони
  не зловлять.
- Форма `defineRoute` — публічна поведінка бекенду: зміна оновлює `documentation/backend/` в обох
  мовах у тому ж PR.
- Контракт мусить жити в `shared`: фронтенд не може імпортувати таблицю маршрутів бекенду, бо вона
  тягне контролери.

## Знайдено під час виконання плану

Не входить у фічі плану; потребує окремого рішення, чи заводити задачі.

- **Епізодичний 503 у live e2e локально.** Двічі за день бекенд відповів 503 на запит, який мав
  пройти: `POST /api/auth/login` (один із 7 прогонів сценарію V02) і перевірка посилання
  `/verify-email` («Service temporarily unavailable», один із 5 повних прогонів під час V05).
  Обидва маршрути проходять через спільні ліміти в Redis, які при недоступності сховища
  відповідають 503 (fail closed), а тайм-аут цього з'єднання — `RATE_LIMIT_REDIS_TIMEOUT_MS=50`.
  Імовірна причина — перевищення 50 мс під навантаженням машини (збірка, Docker). Логами не
  підтверджено: вивід сервера в цих прогонах не зберігався. У CI не спостерігалося.
  **Доповнення 2026-11-11.** Ще два випадки на `POST /api/auth/register/email` (2 падіння з 5 повних
  прогонів live e2e під час C1). Перевірка гіпотези: з `RATE_LIMIT_REDIS_TIMEOUT_MS=1000` — 6
  прогонів із 6 без жодного 503; зі значенням за замовчуванням (50) — 2 з 5. Вибірка мала, але
  узгоджується з причиною «тайм-аут 50 мс, відмова при недоступності сховища лімітів». Питання для
  рішення: чи лишати 50 мс типовим значенням (на завантаженій машині розробника воно дає відмови
  на маршрутах автентифікації), чи підняти його або задати більше лише для live e2e.
- **Нестабільний тест `vendor/start/upload-limits.transport.spec.ts`** («does not buffer 20 parallel
  50 MiB uploads»): в одному з повних прогонів `pnpm test` одне з 20 завантажень отримало
  `400 Bad Request` замість `413 Payload Too Large`. Окремо тест пройшов 8 разів із 8 (5 на гілці
  V04, 3 на незміненому коді). Невідомо, чи це лише тест, чи сервер справді інколи відповідає 400
  на завелике тіло під навантаженням.

- **Нестабільний live e2e `sign-in-redirect.spec.ts` у CI (2026-11-11, PR #519).** Підготовка
  акаунта (`createVerifiedAccount`) один раз отримала `400` на `POST /api/auth/verify-email` з
  посиланням із щойно надісланого листа; повторний запуск job пройшов. Той самий хелпер у тому ж
  прогоні пройшов в інших тестах. Причину не з'ясовано: тіло відповіді не логувалося.
- **`test:e2e:security` локально не стартує** на сервері PostgreSQL без бази за замовчуванням із
  `.env` (`3D000`): конфіг, на відміну від live, не створює й не мігрує свою базу. Запущено з
  `PGSQL_DB_NAME=vibe_e2e_live`.

**Рішення власника 2026-11-11 щодо знайденого:**

- Епізодичний 503 у live e2e: типове `RATE_LIMIT_REDIS_TIMEOUT_MS` піднімається з 50 до 500 мс,
  як у основного клієнта Redis (`REDIS_COMMAND_TIMEOUT_MS`), який у тих самих прогонах не відмовляв
  (`feat-178`).
- Нестабільні тести (`upload-limits.transport.spec.ts`, разовий `400` від `verify-email` у CI,
  тест подвійного кліку на вході під навантаженням): разові збої не відстежуємо, задач не
  заводимо.
- Збій `playwright install-deps` на runner'ах GitHub (недоступні apt-дзеркала): повтор кроку з
  паузами (`feat-179`).
- `test:e2e:security` без бази за замовчуванням: лишається як є; запуск з `PGSQL_DB_NAME`.
