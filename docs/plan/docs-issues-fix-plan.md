Роботи незалежні, але можуть увійти в одну вузьку feature/PR, якщо це відповідає актуальному ownership у `feature_list.json`. Не змінювати `feature_list.json` напряму з feature-гілки.

## 1. Пункт 79 — канонічна помилка HTTP `admin_guard`

У [`admin-guard.ts`](../../packages/backend/src/app/middlewares/admin-guard.ts) дві відмови формують payload вручну. Замінити їх викликом уже наявних helper-ів з `services/shared/errors.ts` та `services/shared/app-error-payload.ts` (або еквівалентного чинного модуля). Не імпортувати controller-шар у middleware й не створювати новий error helper.

Додати/оновити тести для анонімного запиту та користувача без ролі admin: обидва мають дати 403 і канонічний код `forbidden`. Перевірити поточну документацію middleware/auth і змінювати її лише якщо вона показує старий payload.

## 2. Пункт 76 — єдиний часовий пояс для PostgreSQL-з'єднань

Додати `options: '-c TimeZone=UTC'` до наявного `connectionOptions` у [`pool-options.ts`](../../packages/backend/src/database/pool-options.ts). Цей об'єкт уже використовується application main pool і session-check pool.

[`seed.ts`](../../packages/backend/src/db/seed.ts) створює власний `pg.Pool` без `connectionOptions` і записує рядки через `defaultNow()`, тому йому теж передати `options: '-c TimeZone=UTC'`. `create-database.ts` (лише `CREATE DATABASE`) і тестовий `pg-global-setup.ts` не змінювати. `drizzle.config.ts` відкриває з'єднання окремо: додавати параметр туди тільки якщо міграційні/seed сценарії справді залежать від часової зони; не розширювати зміну без такого підтвердження.

Додати тест до наявного `pool-options.spec.ts` на значення `options`. Якщо доступна PostgreSQL test-інфраструктура, перевірити `SHOW TimeZone` для main і session-check pool. У документації коротко зазначити, що application DB connections фіксують UTC.

Не переводити всі колонки на `timestamptz` у межах цього виправлення: це потребує окремої оцінки міграції та сумісності. Не стверджувати, що зміна pool config виправляє прямі зовнішні SQL-клієнти.

## 3. Пункт 77 — необов'язковий `token` у login-схемі

У [`login.ts`](../../packages/shared/src/schemas/auth/login.ts) змінити `token` на опційне поле в обох варіантах схеми (`email` і `identifier`). Залишити приймання наявного поля для сумісності; не прибирати поле з frontend у межах цього виправлення.

Додати shared-тести: login payload без `token` проходить валідацію; payload з рядковим `token` теж проходить. Тут не потрібно додатково переробляти login DTO або вводити нову схему.

## Перевірка завершення

- Цільові тести для admin guard, shared login schema та pool options.
- `pnpm typecheck`, `pnpm lint`, `pnpm test`.
- `pnpm docs:build && pnpm docs:verify`, якщо змінено документацію.
- Ручна перевірка: не-admin на `GET /api/admin/users` отримує 403 з канонічним `code: 'forbidden'`; login payload без `token` проходить валідацію; PostgreSQL application pools працюють у UTC.

Якщо широка перевірка занадто довга для цього PR, пріоритет — цільові тести й `typecheck`/`lint`; пропущені команди записати як неперевірені, не заявляти повний Definition of Done.
