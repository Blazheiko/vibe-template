## Правила

- Кожна фіча — окремий запис у `feature_list.json` через PR у `main`. Id нижче (`S01…`) — робочі;
  реальний id (`feat-195`, …) присвоюється при створенні запису.
- Одна фіча в роботі на власника; `progress.md` і `session-handoff.md` — на гілці фічі.
- Шаблон без продакшену: без зворотної сумісності, перехідних шарів і міграції даних.
- Зміна публічної поведінки бекенду (env, маршрут, middleware, схема) оновлює сторінку в
  `documentation/backend/` в обох мовах у тому ж PR; `pnpm docs:build && pnpm docs:verify`.
- `session_web` / `csrf_guard` лишаються явними на групі маршрутів; глобальне підключення не
  пропонується.

### Definition of Done (доповнення до `AGENTS.md`)

- `pnpm typecheck`, `pnpm lint`, `pnpm test`, ручна перевірка, evidence у `progress.md`.
- Фіча з позначкою **PG** або **Redis** також вимагає `pnpm --filter backend test:pg` / `test:redis`
  на піднятих тестових сервісах; у evidence — вивід, де цільові тести виконані, а не пропущені.
- Фіча з позначкою **e2e** вимагає `pnpm --filter frontend test:e2e`.
- Кожне виправлення має тест, що падає до зміни.
- Тести гонок і порядку подій використовують керовані бар'єри (deferred-проміс), а не `setTimeout`.
- Останній PR плану додає в `docs/security/security-review-2026-11-12.md` таблицю стану
  (знахідка → фіча → PR → тест), за зразком `docs/security/security-analysis-status.md`.

## Опис фіч

### S01. WS Closes On Session Revocation (M-1)

Відкликання сесії закриває відкриті сокети користувача.

- У `ws-connection-registry.ts` — `closeUserConnections(userId, exceptSessionId?)`, що викликає
  `ws.end(4001)` для кожного з'єднання користувача.
- Виклики: logout (лише з'єднання цієї сесії), logout-all, зміна пароля, скидання пароля через
  пошту і телефон, claim акаунта — усюди, де ротується `users.session_token`.
- Для кількох інстансів: періодична перевірка (зараз лише роль адміна в
  `admin-ws-access-service.ts`) порівнює `userData.userToken` кожного з'єднання з
  `users.session_token` одним пакетним запитом і закриває розбіжності.
- Перевірити припущення звіту про `sendPingsAutomatically`; результат записати в evidence.
- Документація: `documentation/backend/websocket.md` (розділ «Обмеження та безпека»), uk + en.

Приймання:

- Тест: сокет, що після підписки шле лише `ping`, закривається з кодом 4001 одразу після
  logout-all / зміни пароля / скидання в тому ж процесі.
- Тест: з'єднання з застарілим `userToken` закривається періодичною перевіркою (ротація зроблена
  «іншим інстансом», тобто напряму в БД).
- Тест: logout однієї сесії не закриває сокети інших сесій користувача.
- Після закриття сокет не отримує `admin_user_online_upsert` і `broadcastMessageToUser`.

### S02. One-Time WS Token (L-12)

- `verifyUpgradeToken` читає токен через `GETDEL`; `sessionId` і `userToken` живуть лише в
  `userData`.
- `onRefreshToken` / `onRevokeToken` і `EXPIRE` на кожне повідомлення та ping видаляються.
- Клієнт (`useWebSocketConnection.ts`) бере новий токен перед кожним перепідключенням —
  перевірити, що так і є; виправити, якщо ні.
- Документація вже описує токен як одноразовий — звірити формулювання.

Приймання: другий upgrade з тим самим токеном → 401; на повідомлення й ping немає команд Redis для
токена; перепідключення клієнта після обриву працює (наявні e2e).

### S03. WS Connection Limits (M-4, L-11, L-13)

- Ліміт одночасних з'єднань на користувача і на IP у `handleUpgrade` / `handleConnected` (Д1); env
  з типовими значеннями; лічильники зменшуються при закритті.
- L-11: бінарний фрейм закриває з'єднання з кодом 1003; рівень логу `warn`.
- L-13: ключ per-route ліміту — `userData.userId` (разом з IP).
- Повідомлення з невідомою подією: відтворити вартість (Redis + перевірка сесії); після S02 команд
  Redis на повідомлення немає, лишається `findSessionToken` — перевіряти сесію лише після того, як
  маршрут знайдено.

Приймання: 11-те з'єднання користувача → 429; після закриття одного — upgrade проходить; бінарний
фрейм → закриття 1003 і один рядок `warn`; два користувачі з одного IP мають окремі per-route
бюджети; невідома подія не викликає запиту до пулу перевірки сесій.

### S04. Sign-in Method Added Notification (M-2, частина 1)

- Нова подія `sign_in_method_added` у `SecurityEvent` і шаблон листа з назвою провайдера та іменем
  профілю (очищеним, див. S09).
- Надсилається з `confirmLink` і `linkTrusted` замість `new_sign_in`.

Приймання: тест на обидва шляхи; знімок шаблону; у листі немає сирого `providerName` з URL чи
переносами.

### S05. Linked Sign-in Methods Management (M-2, частина 2)

- Репозиторій: `deleteByIdForUser`; `findByUserId` уже є.
- Маршрути у веб-групі (`session_web` + `csrf_guard`): список прив'язок і відв'язування. Через скіл
  `backend-feature`, з контрактом маршруту (ADR 0005).
- Відв'язування вимагає повторної автентифікації (Д3) і забороняє видаляти останній спосіб входу
  (немає пароля, немає підтвердженого телефону, остання прив'язка).
- Після відв'язування — сповіщення користувачу.
- Фронтенд: блок «Способи входу» в `UserAccount.vue`.
- Д2: лист «пароль змінено» і сторінка після скидання перелічують прив'язані способи входу.
- Документація: сторінки OAuth і маршрутів у `documentation/backend/`, uk + en.

Приймання: IDOR-тест (чужа прив'язка → 404); відв'язування без повторної автентифікації → 403;
останній спосіб входу → 409; після відв'язування вхід через цього провайдера не потрапляє в акаунт;
e2e на золотий шлях.

### S06. OAuth Flow Hardening (L-6, L-7, L-8, L-9, I-2)

- L-6: `Sec-Fetch-Site: cross-site` на `…/redirect` → відмова (Д4).
- L-7: `oauthProvider` зберігається разом зі state і перевіряється в `consumeSessionData`; PKCE для
  GitHub і GitLab (перевірити підтримку за актуальною документацією провайдерів; Facebook — лише
  якщо підтримує).
- L-8: GitLab без `email_verified === true` → наявна помилка «Could not retrieve email from
  provider».
- L-9: `providerName` обрізається до 255; `providerAvatar` довший за 500 → `null` (в `identity` і в
  `extra` pending-прив'язки).
- I-2: аватар від провайдера приймається лише як `https://`-URL, інакше `null`.

Приймання: state, виданий для google, не приймається на github callback; запит авторизації GitHub
і GitLab містить `code_challenge`; вхід з іменем на 300 символів і аватаром на 600 проходить;
cross-site redirect відхилено, same-site і без заголовка — проходять.

### S07. In-Flight Body Budget (M-3, частина 1)

- У `readData` — глобальний і per-IP лічильник буферизованих байтів. Перевищення → 503 (глобальний)
  або 429 (per-IP) з `Connection: close`; лічильник зменшується при завершенні, abort і помилці.
- Пороги — env з типовими значеннями (пропозиція: 256 МіБ глобально, 16 МіБ на IP); значення
  уточнити під час реалізації й описати в документації поруч з оцінкою пам'яті.
- Перевірити неперевірене у звіті: як довго uWS тримає зупинене з'єднання; за потреби — тайм-аут
  читання тіла.
- Оновити `docs/plan/http-body-limits-plan.md:59` (застереження стає закритим) і
  `documentation/backend/` (env, ліміти), uk + en.

Приймання: transport-тест — N завислих POST з одного IP, наступний отримує 429, з іншого IP —
проходить; після abort лічильник повертається до нуля (без витоку); глобальний поріг дає 503.

### S08. Pre-Auth Body Limits (M-3, частина 2)

- Типовий `APP_MAX_JSON_BODY_SIZE` → 100 КБ; маршрути, яким треба більше (статті бази знань,
  промпти — скласти перелік), отримують явний ліміт маршруту (механізм уже є, feat http-body-limits).
- `rateLimit` на admin-групу бази знань (маршрут `uploadScreenshot`).
- Для multipart-маршрутів у веб-групах — синхронна перевірка наявності підписаної session cookie
  до читання тіла; без неї 401 без буферизації. Вмикається позначкою маршруту, а не глобально.

Приймання: JSON 150 КБ на звичайний маршрут → 413, на маршрут статті — проходить; multipart без
cookie → 401, і `readData` не викликано; 11-те завантаження скриншота за хвилину → 429.

### S09. Verification Mail Abuse (L-1, L-2)

- L-1 (Д5): листи на ще не підтверджену адресу (реєстрація, `link-email/start`, повторне
  надсилання) не містять імені; `providerName` у листі прив'язки OAuth очищається (без URL і
  керівних символів, обрізаний).
- L-2: повторний лист при вході ділить ліміт з `resendVerificationUser` (3/год) і має добовий
  ліміт (5/добу на акаунт).

Приймання: знімки шаблонів без імені; `name` з URL не з'являється ні в HTML, ні в текстовій
частині; четвертий вхід непідтвердженим акаунтом за годину не надсилає лист, відповідь та сама.

### S10. Phone Reset Hardening (L-3, L-4)

- L-3 (Д6): `reset-phone/start` з іншої сесії відкриває власний challenge (до 2 живих на номер);
  захист feat-160 від скасування чужого скидання зберігається (його тест лишається зеленим).
  Вичерпання SMS-бюджету — прийнятий ризик у `documentation/backend/` і в коментарі
  `config/auth.ts`.
- L-4а: лічильник помилкових кодів на номер з вікном 24 год (10 помилок блокують скидання).
- L-4б: `issueSmsChallenge` у скиданні виконується у фоні після відповіді, як для пошти.

Приймання: власник отримує робочий `challengeId`, поки живий challenge зловмисника; 11-та помилка
за добу → відмова навіть з новим challenge; час відповіді для відомого й невідомого номера не
залежить від провайдера (тест з керованим бар'єром у фейковому провайдері).

### S11. Sentry Replay Without URL Tokens (L-17)

- `beforeAddRecordingEvent` маскує `data.href` і URL у `data.payload` наявним `maskUrl`.
- Event processor для `event.type === 'replay_event'` маскує `urls` і `request.url`.
- `ResetPasswordView`, `VerifyEmailView`, `OAuthLinkConfirmView` читають токен у пам'ять і
  прибирають його з адреси через `router.replace`.
- Тест на справжньому SDK (як `sentry-tracing.spec.ts` у feat-194): токен-канарка не потрапляє в
  жоден відправлений envelope при ввімкненому replay.
- Документація: `documentation/backend/observability` і сторінка Sentry фронтенду, uk + en.

Приймання: тест падає на старому коді; e2e — після відкриття `/reset-password?token=…` адресний
рядок без токена, скидання працює, перезавантаження сторінки показує зрозумілу помилку.

### S12. HTTP Core and Cookie Lows (L-5, L-14, L-15, L-16)

- L-5: рядок `SESSION_COOKIE_HOST_PREFIX=false` у `.env.example` закоментовано; `validateRuntimeConfig`
  кидає помилку, коли `isProductionLike` і cookie без `Secure` чи без `__Host-`.
- L-14: один агрегований рядок `debug` на запит для невалідних заголовків; `Rate limit exceeded` —
  не частіше одного рядка на ключ за вікно.
- L-15: `getAssetCspKind` повертає `'document'` для `html` / `htm` і для disk-записів.
- L-16: `route.method` у ключі per-route ліміту.

Приймання: старт із `APP_IS_PRODUCTION=true` і вимкненим префіксом завершується помилкою з назвою
змінної; 100 невалідних заголовків → один рядок логу; HTML понад 1 МіБ віддається з CSP; GET і POST
одного URL мають окремі лічильники.

### S13. Supply Chain Pinning (L-18, L-19, I-4, I-5)

- L-18 (Д7): digest базового образу в обох стадіях; NodeSource через apt-ключ і список

- L-19: `pnpm.onlyBuiltDependencies: ["esbuild"]` (перевірити, чи потрібен `uWebSockets.js`);

з нуля проходить без попереджень про заблоковані скрипти, що потрібні збірці; `make check` зелений.

### S14. Push and Cleanup Lows (L-10, I-3, I-6, I-7, I-1)

- I-7 (Д8): `PASSWORD_MAX_LENGTH = 128`; перевірити, що форми й тексти помилок беруть значення зі

- I-1: абзац у `documentation/backend/` (AI / підтримка): системний prompt і активні статті бази
  знань вважаються доступними користувачеві, секретів у них не тримати. Змін у коді немає.
