# План: production-compose і деплой на Hetzner через Dokploy

**Статус: погоджено** (2026-11-14): рішення Д1–Д9 прийнято власником; 2026-11-25 власник змінив Д2: PostgreSQL і Redis створюються вручну в панелі Dokploy як сервіси Database, а не в compose-файлі (Д2, Д5, Д6, Д7, Д10 і пов'язані розділи оновлено). Фіча: `feat-218` (id присвоюється в PR у `main`). Залежить від `feat-217` ([план лендінгу](./landing-plan.md)): потрібні образ лендінгу і контракт URL.

## Задача

`docker-compose-prod.yml` у корені, який розгортає застосунок (міграції, backend із SPA, лендінг) як один Compose-сервіс у Dokploy на сервері Hetzner, і сторінка документації з покроковим деплоєм. PostgreSQL (pgvector) і Redis користувач відкриває руками в панелі Dokploy як окремі сервіси Database; compose до них лише підключається.

## Перевірка без сервера

- **Статична:** `scripts/verify-compose.mjs` перевіряє й `docker-compose-prod.yml`: `docker compose -f docker-compose-prod.yml --env-file .env.prod.example config` проходить; без обов'язкової змінної — падає з її назвою; у жодного сервісу немає `ports`; у `app` і `landing` є `healthcheck` і `restart`; `API_PATH_PREFIX` у build-arg і runtime той самий; `LANDING_APP_URL` = `APP_URL`, `LANDING_SITE_URL` = `LANDING_URL`; сервісів `postgres`/`redis` і volume у файлі немає; `app` і `migrate` у зовнішній мережі `dokploy-network`. Запускається в `make check` і CI `quality`.
- **Димовий запуск:** `docker-compose-prod.smoke.yml` — override лише для локальної перевірки: Caddy з `tls internal` на `https://app.localhost` і `https://landing.localhost` (браузери і curl резолвлять `*.localhost` в `127.0.0.1`), SeaweedFS (S3, як у dev-compose) і Mailpit замість зовнішніх сервісів, `LANDING_STRICT=false`, а також `postgres` (`pgvector/pgvector:pg16`) і `redis` замість баз Dokploy і локальна мережа з іменем `dokploy-network` замість зовнішньої. `make prod-smoke` піднімає production-compose з цим override і запускає `verify-landing-deploy.sh --insecure`, `/api/ready`, реєстрацію і вхід через API (curl). Перевіряє саме production-режим (`APP_IS_PRODUCTION=true`, Secure-cookie, `__Host-`), а не local.

## Документація

Нова сторінка `documentation/guide/deployment-dokploy.md` (+ `en/`), сайдбари обох локалей, `KEY_PAGES`/`EN_KEY_PAGES`; посилання з `backend/deployment.md` і `guide/landing.md`; коментар-шапка `docker-compose.yml` посилається на production-файл. Структура:

1. **Топологія:** схема «Hetzner-сервер → Traefik (Dokploy) → `landing` / `app` → PostgreSQL і Redis (сервіси Database Dokploy, `dokploy-network`); зовнішні S3 і SMTP»; таблиця «Контракт URL» з production-значеннями.
2. **Передумови:** сервер Hetzner Cloud (Ubuntu 24.04; від 4 GB RAM — збірка frontend на сервері; інакше swap), DNS A-записи `example.com`, `www`, `app` на IP сервера, встановлений Dokploy (посилання на його інструкцію), Cloud Firewall (Д7), бакет Hetzner Object Storage з CORS за `corsS3.prod.example.xml`, SMTP-провайдер.
3. **Підготовка репозиторію:** `PRODUCT.siteUrl`, тексти лендінгу, гілка для деплою.
4. **Бази в Dokploy (вручну):** Project → Create Service → Database → PostgreSQL: Docker image `pgvector/pgvector:pg16`, назва бази, користувач, пароль, External Port порожній, Deploy; так само Redis з паролем. Де взяти Internal Credentials для Environment.
5. **Застосунок у Dokploy:** Project → Create Service → Compose (тип Docker Compose); Provider — git, гілка, compose path; Environment — вставити `.env.prod.example` і заповнити, зокрема адреси й облікові дані баз; `TRUSTED_PROXY_CIDRS` — команда для визначення; Domains — два домени з портами `3000` і `8080`, HTTPS; Deploy; AutoDeploy webhook.
6. **Перший деплой:** що відбувається (збірка, `migrate`, старт), де дивитися логи, seed (Д8).
7. **Перевірка:** `scripts/verify-landing-deploy.sh https://example.com https://app.example.com`, `curl https://app.example.com/api/ready`, вхід і реєстрація з кнопок лендінгу, перевірка підробленого `X-Forwarded-For` з `backend/deployment.md`.
8. **Оновлення і відкат:** push у гілку → AutoDeploy; відкат — redeploy попереднього коміту; міграції лише вперед (відкат схеми — вручну, з бекапу).
9. **Бекапи і відновлення** (Д6): вкладка Backups сервісу PostgreSQL, ручний `pg_dump` і відновлення.
10. **Чекліст і усунення проблем:** `migrate` не підключається до бази (бази не створено, не той Internal Host, compose не в `dokploy-network`), `CREATE EXTENSION vector` падає (образ без pgvector), 502 (не той порт у Domains), cookie не встановлюється (`APP_URL` не `https`), SPA ходить не туди (`API_PATH_PREFIX`), усі запити з одного IP (`TRUSTED_PROXY_CIDRS`), збірка падає з OOM (пам'ять сервера), лендінг не збирається (строгий режим і адреси).

## Ризики

- **Пам'ять сервера під час збірки** — frontend збирається на сервері; на 2 GB можливий OOM. Документується мінімум і swap; збірка в CI + registry — окремий пункт.
- **Traefik і `X-Forwarded-For`** — чи перезаписує Traefik заголовок від клієнта за налаштувань Dokploy за замовчуванням, перевіряється на кроці 7. Якщо ні — у документацію додається налаштування `forwardedHeaders` entrypoint або middleware.
- **`validate-runtime-config` і `*.localhost`** у димовому запуску — production-режим може відхиляти localhost-адреси; перевіряється на кроці 5, тоді smoke використовує інший локальний домен (наприклад, `*.test` через `/etc/hosts`).
- **Ізольовані деплої Dokploy** змінюють мережу сервісів: compose має лишатися в `dokploy-network`, інакше бази недоступні. Інструкція фіксує налаштування, з яким перевірено.
- **Бази поза compose** — `depends_on` на них немає; якщо база ще стартує, `migrate` падає і деплой треба повторити. Перевіряється на кроці 7; за потреби `migrate` чекає на базу з обмеженим тайм-аутом.
- **Redis без бекапу** — після втрати volume зникають дані Redis; що саме (сесійні кеші, лічильники rate limit тощо), перелічує інструкція.

## Поза фічею

- Збірка образів у CI і публікація в registry (GHCR), деплой готових образів.
- Кілька реплік `app`, Docker Swarm (режим Stack).
- Керований PostgreSQL замість контейнера.
- Rate limit на рівні Traefik.
