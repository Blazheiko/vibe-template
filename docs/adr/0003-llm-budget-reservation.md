# ADR 0003: добовий LLM-бюджет користувача — атомарне резервування в Redis зі звіркою

- **Статус:** запропоновано 2026-11-01; реалізація — feat-063, частина D2.
- **Дата запису:** 2026-11-01.
- **Джерело:** [`docs/security/code-review-main-2026-10-31.md`](../security/code-review-main-2026-10-31.md); план — [`docs/plan/code-review-fixes-tasks.md`](../plan/code-review-fixes-tasks.md), фаза D2.

## Контекст

Кожне повідомлення чату підтримки — до трьох платних викликів провайдера: переклад запиту, embedding і відповідь (`support-service.ts` → `support-query-translation-service.ts`, `support-embedding-service.ts`, `support-llm-service.ts`). Обмеження на кількість (ADR-незалежні частини D0/D1: довжина, частота, «одна відповідь за раз») не обмежують **вартість**: 20 повідомлень на хвилину по 4000 символів — це необмежені гроші за добу.

Стан коду на `21d9a57`:

1. `llmUsageService.recordText` ([`llm-usage-service.ts`](../../packages/backend/src/app/services/ai/usage/llm-usage-service.ts)) — fire-and-forget: помилка запису лише логується, `totalTokens` може бути `null` (провайдер не повідомив usage, виклик перервано). Це **аудит**, не облік для ухвалення рішень.
2. Перевірка «залишок → запуск» не може спиратися на `llm_text_usage`: запис відбувається після відповіді, тому N паралельних запитів бачать той самий залишок, а зараз ще й запис асинхронний.
3. Токени відомі точно лише після виклику; до нього є лише оцінка.

## Рішення

1. **Облік для рішень — лише Redis.** Ключ `llm:budget:<userId>:<YYYY-MM-DD>` (дата за UTC, значення — витрачені токени, TTL 48 год). `llm_text_usage` лишається аудитом і для enforcement не читається.
2. **Перевірка і резервування — одна атомарна операція** (Lua): `if used + reserve > limit then return -1 end; INCRBY; (перший запис ставить TTL)`. На відмові нічого не змінюється, тож «повертати» нічого. Резерв не перевищує ліміт (інакше при малому ліміті користувач не міг би написати нічого).
3. **Резервування — частина допуску** (`admit()` у `support-service.ts`), після throttle і замка: відмова бюджету — це відповідь на запит (`429`, `reason: support_budget_exceeded`, `retryAfterSeconds` до кінця доби UTC), а замок, узятий цим допуском, **звільняється** (тест: «замок взято → бюджет відхилено → замок вільний»). Недоступність Redis — `503`, як і для throttle (fail-closed).
4. **Резерв — оцінка всього pipeline, розкладена по викликах:** переклад = `токени(повідомлення) + maxTokens(переклад)`; embedding = `токени(повідомлення)`; відповідь = `AI_SUPPORT_PROMPT_ALLOWANCE_TOKENS + токени(повідомлення) + maxTokens(відповідь)`. `токени(текст) = ⌈символи / 2⌉` — **евристика, а не верхня межа** (CJK, emoji, код можуть бути гіршими). `maxTokens` — справжня межа виходу (з `prompts`, інакше `config/support.ts`). `AI_SUPPORT_PROMPT_ALLOWANCE_TOKENS` покриває системний промпт, контекст бази знань і історію, розмір яких на допуску невідомий. Привітання — лише виклик «відповідь» без повідомлення.
5. **Звірка — одна, у кінці запуску** (`release()` допуску, на кожному шляху, перед зняттям замка). Для кожного виклику:
    - **не стартував** (запуск зупинено до відправки: втрачений замок, закрите з'єднання, дублікат повідомлення, помилка валідації) → його частка **повертається** повністю;
    - **стартував і провайдер повідомив usage** → списується **фактичне** `totalTokens` (звірка вниз або вгору);
    - **стартував, а usage немає** (abort посеред стрімінгу, timeout, помилка провайдера) → **резерв лишається списаним** як консервативний факт.
      Підсумкова поправка — один `INCRBY (фактично − резерв)` по ключу **дня резервування** (не дня звірки). Клієнт, що скасував після старту генерації, платить резерв.
6. **Помилка звірки не відкликає відповідь:** вона логується, резерв лишається (консервативно). Якщо процес помер — теж. Резерв ніколи не «губиться» в бік заниження.
7. **Конфігурація:** `AI_SUPPORT_DAILY_TOKEN_BUDGET` (за замовчуванням 200000; `0` вимикає облік — лише поза production-like середовищем, інакше помилка старту), `AI_SUPPORT_PROMPT_ALLOWANCE_TOKENS` (за замовчуванням 8000). Окремого `AI_BUDGET_RESERVE_RATIO`, згаданого в плані, **немає**: множник на евристику ховає той самий невідомий розмір контексту, а `ALLOWANCE` називає його прямо.
8. **Клієнт Redis:** строгий клієнт rate-limit (`redis-rate-limit.ts`: без offline-черги, без повторної відправки команд, `commandTimeout`), як у `consumeAuthThrottle` — скрипт, що міг уже виконатися, не відправляється вдруге.

## Розглянуті альтернативи

- **Перевірка за `llm_text_usage` (SUM за добу).** Відхилено: запис асинхронний і може не відбутися; N паралельних запитів бачать той самий залишок; запит до БД на кожне повідомлення.
- **Резервування без звірки (фіксована ціна повідомлення).** Відхилено: ціна залежить від моделі, довжини й історії; без звірки бюджет або порожній, або безглуздий.
- **Повернення всього резерву при помилці/abort.** Відхилено: після старту генерації провайдер уже порахував токени; повне повернення дало б безкоштовні запити, які користувач скасовує після початку (атака на вартість).
- **Звірка після кожного виклику.** Відхилено: три `INCRBY` замість одного без виграшу — користувач і так не може запустити другу відповідь, поки перша не завершилася (замок).
- **Ліміт у токенайзері провайдера (`estimateTokens`).** Відхилено для цієї ітерації: потрібна залежність на токенайзер кожного провайдера (openai/xai/mistral); евристика + звірка дає порядок величини. Токенайзер можна підставити в `токени(текст)` пізніше без зміни контракту.

## Наслідки

- Гарантія **приблизна**: резерв — оцінка, звірка коригує в обидва боки; бюджет обмежує вартість за добу на порядок величини, а не з точністю до токена. Остання відповідь доби може вийти за ліміт на різницю «фактично − резерв», але не більше ніж на одну відповідь (замок).
- Консервативний резерв означає, що користувач упирається в ліміт трохи раніше за реальні витрати (доки не відбулася звірка попередньої відповіді, її резерв зайнятий).
- +1 Redis-команда на допуск (резервування) і +1 на завершення (звірка).
- Адмін-ендпойнт перегляду/скидання бюджету — окремий PR, якщо буде потрібен.
