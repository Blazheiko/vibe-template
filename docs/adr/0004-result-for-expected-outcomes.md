# ADR 0004: `Result` лише для очікуваних результатів, збої інфраструктури кидаються

- **Статус:** прийнято 2026-11-02; реалізація — feat-089 і два наступні PR етапу 4.
- **Дата запису:** 2026-11-02.
- **Джерело:** code review `main` (2026-11-02); план — [`docs/plan/error-handling-fix-plan.md`](../plan/error-handling-fix-plan.md), етап 4.

## Контекст

Сервіси повертають `AppResult<T>` (`better-result`). Окрім очікуваних відповідей (`invalid credentials`, `not found`, `conflict`, throttling) у `Result` загорнуто й кожен виклик БД, Redis, S3 чи хешування: `tryInternal(() => repo.x(), 'Failed to …')` і ручне прокидання `if (Result.isError(r)) return Result.err(r.error)`. На `152ca34` було 108 викликів `tryInternal` і 147 таких прокидань.

Наслідки цього:

1. Неочікувані збої вже обробляє глобальний обробник (`classifyError`, feat-087): 500, або 503 для Redis, з логом і подією в Sentry. Обгортка дублює його.
2. До feat-086 обгортка губила лог і Sentry-подію: причина лежала в `AppError.cause`, і її ніхто не логував.
3. Код сервісу наполовину складається з прокидання помилок (`authService.login`), і за ним важко побачити бізнес-логіку.

## Рішення

1. **`Result<T, AppError>` — лише для того, що клієнт має розрізняти:** `BadRequest`, `Unauthorized`, `Forbidden`, `NotFound`, `Conflict`, `RateLimited`, `UpstreamError` / `UpstreamTimeout` (помилки AI-провайдера з власним кодом) і `ServiceUnavailable` там, де сервіс свідомо відмовляє (наприклад, AI-провайдер не налаштований).
2. **Збої інфраструктури кидаються.** Сервіс не обгортає виклик репозиторію, Redis чи S3. Виняток доходить до `handleError` (HTTP) або WS-диспетчера, а `classifyError` дає 500 `internal_error`, або 503 `service_unavailable` з `Retry-After` і `sentrySkip` для Redis.
3. **Виняток не змінює того, що запит уже вирішив про відповідь.** Шлях винятку в `server.ts` пише cookies, виставлені до збою (сесію могли вже замінити), викликає `session.beforeSend` і ставить CORS-заголовки, як звичайна відповідь.
4. **Свідомий перехват лишається явним:** best-effort кроки (видалення старого аватара, скидання лічильника throttle) ловлять виняток локально і пишуть `warn`; відома помилка БД, яка означає бізнес-результат (унікальний індекс `23505` → `conflict`), ловиться `try/catch` у місці виклику.
5. **Фонові задачі** (`void promise`) мають власний `catch` з логом: виняток з них ніхто не обробить.
6. Де лишається кілька послідовних кроків з `Result`, допускається `Result.gen` + `yield*` (`better-result@3`).

## Розглянуті альтернативи

- **Лишити `tryInternal` і лише логувати `cause` (feat-086).** Це вже зроблено як страховка, але дублювання й шум у сервісах лишаються.
- **Перевести все на винятки, включно з бізнес-помилками.** Відхилено: очікувані відповіді — частина контракту сервісу, тип `AppResult` робить їх видимими в сигнатурі, а контролер мапить їх без `try/catch`.
- **`Result.gen` скрізь замість винятків.** Відхилено як головний механізм: генератор прибирає прокидання, але інфраструктурні збої все одно не мають бути частиною типу результату.

## Наслідки

- Публічний текст інфраструктурної 500 стає `Internal server error` замість `Failed to upload avatar` тощо. Зворотна сумісність не потрібна (шаблон без продакшну); frontend і тести оновлюються в тому ж PR.
- Тести сервісів на збій репозиторію перевіряють `rejects`, а не `Result.err` з `Internal`.
- Шаблон нового сервісу (`documentation/backend/services.md`, `adding-a-feature.md`) показує виклик репозиторію без обгортки.
