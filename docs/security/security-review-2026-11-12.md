Примітки:

1. **OAuth (feat-200).** Перевірено тестами з підставним клієнтом провайдера; на справжніх Google, GitHub і GitLab потік не запускався.
2. **L-14.** Звіт каже «будь-який байт понад 0x7E у значенні». На живому стеку значення з UTF-8 (`café`) невалідним не вважалося, невалідне ім'я заголовка — вважалося. Виправлення від цього не залежить: рядок логу тепер один на запит для будь-яких відхилених заголовків. Причину з'ясовано у feat-215: uWebSockets.js 20.71.0 обрізає байти понад 0x7F на краях значення так само, як пробіли (`café` надходить як `caf`, `écafe` як `cafe`). Байт понад 0x7E усередині значення доходить до перевірки й відхиляється. Тож такий байт до застосунку не потрапляє в жодному випадку; поведінку зафіксовано тестом `vendor/utils/network/header-values.live.spec.ts` на справжньому сервері.
3. **L-17.** Запропонованого у звіті маскування виявилося замало: replay записує адресу сторінки в подіях DOM-рекордера, які SDK не передає в hook. Тому токен прибирається з адреси ще до старту Sentry, а маскування лишилося другою лінією.
4. **L-19.** `audit.yml` запускається за розкладом і вручну; у GitHub Actions він ще не виконувався, обидві його команди запускалися локально. PR від Dependabot для npm потребують увімкненого «Dependabot security updates» у налаштуваннях репозиторію.
5. **Повторна перевірка `main` @ `76c18a7` (2026-11-13)** знайшла чотири прогалини у виправленнях; кожну закрито власною фічею:

    - **L-17 → feat-211 (#641).** Токен прибирається з адреси лише для точного написання шляху. Vue Router приймає також `/reset-password/` і `/Reset-Password`; для них токен лишається в адресі й потрапляє в Replay (відтворено в браузері).
    - **I-7 → feat-211 (#641).** Поле пароля у `VerifyEmailView.vue` лишилося з `maxlength="32"`.
    - **L-3 → feat-212 (#643).** Старт скидання за телефоном витрачає годинний SMS-бюджет номера до остаточної перевірки під блокуванням: два паралельні старти витрачають бюджет двічі, хоча один з них відхиляється. Відтворено PG-тестом: 8 паралельних стартів списували 8 одиниць бюджету за 1 челендж.

## Середні

### M-1. Відкликана сесія не закриває відкритий WebSocket

- **Де:**
    - `vendor/utils/network/ws-handlers.ts:318-334` — гілка `ping` не перевіряє сесію;
    - `vendor/utils/network/ws-handlers.ts:401-410` — сесія перевіряється лише для не-ping повідомлення;
    - `app/services/admin/admin-ws-access-service.ts:49-93` — періодична перевірка дивиться лише на роль;
    - `vendor/start/server.ts:114-118` — `idleTimeout: 120`.
- **Причина:** жоден із потоків logout, logout-all, зміни чи скидання пароля не закриває сокети користувача. `ws.end(4001)` викликається лише в `onOpen` і в `closeExpiredSession`, а остання спрацьовує тільки тоді, коли клієнт сам надішле не-ping повідомлення.
- **Сценарій:**
    1. Зловмисник має викрадену session cookie адміна.
    2. Викликає `update-ws-token`, відкриває сокет, один раз шле `admin/subscribe_online_users`, далі — лише `ping`.
    3. Жертва змінює пароль або натискає «вийти всюди»; `users.session_token` ротується.
    4. Сокет зловмисника лишається в реєстрі й підписаним на топік `admin`.
- **Наслідок:** зловмисник і далі отримує `admin_user_online_upsert` (id, ім'я, email, user agent кожного, хто з'являється онлайн). Для звичайного користувача так само продовжують надходити події `broadcastMessageToUser`, зокрема відповіді чату підтримки (`app/services/support/support-service.ts:54-70`).
- **Звірено:** так. Не перевірено: припущення, що типовий `sendPingsAutomatically` uWS тримає мовчазний сокет живим.
- **Стан:** `documentation/backend/websocket.md` (розділ «Обмеження та безпека») описує, що відкликання не закриває з'єднання одразу, але без наслідку для admin-каналу й без фічі на виправлення.
- **Виправлення:**
    - додати в реєстр `closeUserConnections(userId, exceptSessionId?)` з `ws.end(4001)`;
    - викликати його з logout, logout-all, зміни пароля і потоків скидання;
    - для кількох інстансів розширити 30-секундну перевірку: порівнювати `userToken` кожного з'єднання з `users.session_token` і закривати розбіжності для всіх з'єднань, а не лише адмінських.

### M-2. Прив'язана OAuth-ідентичність невидима й невідкличувана

- **Де:**
    - `app/services/auth/oauth-service.ts:731-753` — вхід за наявною прив'язкою завжди бере поточний `sessionToken`;
    - `app/services/auth/oauth-service.ts:518-523` — після підтвердженої прив'язки надсилається сповіщення `new_sign_in`;
    - `app/services/auth/account-claim-service.ts:79-91` — для підтвердженого акаунта прив'язки не чіпаються;
    - `app/repositories/auth/oauth-account-repository.ts` — є лише `deleteByUserId` (сценарій claim), немає видалення однієї прив'язки чи списку для користувача.
- **Причина:** немає ні endpoint, ні UI для перегляду й видалення прив'язаних ідентичностей; у `SecurityEvent` немає події «додано спосіб входу».
- **Сценарій:**
    1. Зловмисник має короткочасний доступ до пошти жертви (викрадена поштова сесія, правило пересилання, спільний пристрій).
    2. Входить власним акаунтом GitHub/GitLab/Facebook з адресою жертви або відкриває надісланий лінк у своєму браузері.
    3. `confirmLink` створює рядок `oauth_accounts` для підтвердженого акаунта жертви.
- **Наслідок:** жертва бачить лише «новий вхід». Скидання пароля, зміна пароля і logout-all ротують `session_token`, але OAuth-вхід читає поточний токен, тож доступ зловмисника зберігається безстроково. Побачити чи прибрати прив'язку жертва не може. Для порівняння: скидання пароля через пошту помітне й скасовується наступним скиданням.
- **Звірено:** так.
- **Виправлення:**
    - сповіщення `sign_in_method_added` з назвою провайдера і профілю — у `confirmLink` і `linkTrusted`;
    - список і відв'язування `oauth_accounts` на сторінці акаунта, з повторною автентифікацією і забороною видаляти останній спосіб входу;
    - розглянути видалення (або пропозицію видалити) OAuth-прив'язок при скиданні пароля через пошту.

### M-3. Тіло запиту буферизується до автентифікації без ліміту на сумарний обсяг

- **Де:**
    - `vendor/start/server.ts:498-519` — `readAndParseBody` виконується до `executeMiddlewares` (сесія, CSRF, auth, admin);
    - `vendor/utils/network/http-request-handlers.ts:119-138` — усе тіло тримається в пам'яті до `isLast`;
    - `config/rate-limit.ts:18` — глобальний ліміт 600 запитів/хв на IP;
    - `config/app.ts:68-71` — JSON 2 МіБ, multipart 50 МіБ за замовчуванням;
    - `app/routes/http-routes.ts:351-357, 388-391` — маршрут `uploadScreenshot` (5 МБ) у групі без `rateLimit`, на відміну від групи avatar (`:298`).
- **Причина:** єдиний бар'єр перед читанням тіла — лічильники запитів на IP. Вони рахують початки запитів, а не обсяг одночасно буферизованих даних.
- **Сценарій:** неавтентифікований клієнт з однієї IPv4-адреси відкриває 600 з'єднань на будь-який JSON POST без власного ліміту маршруту, у кожному шле `Content-Length: 2097152` і майже все тіло, після чого зупиняється.
- **Наслідок:** близько 1,2 ГБ буферів у пам'яті (до 2,4 ГБ на межі вікна) — достатньо для OOM типового контейнера. Кілька IP або IPv6 /64 множать ефект. Multipart-варіант: завантаження скриншотів бази знань і аватара буферизується повністю ще до відповіді 401/403.
- **Звірено:** частково. Порядок кроків і відсутність ліміту підтверджено. Не перевірено: як довго uWS тримає зупинене чи повільне з'єднання.
- **Стан:** `docs/plan/http-body-limits-plan.md:59` містить лише оцінку `concurrent × maxMultipartBodySize × 2` як застереження; кількість одночасних запитів нічим не обмежена, аспект «до автентифікації» не записаний.
- **Виправлення:**
    - глобальний і per-IP лічильник байтів «у польоті» в `readData`; при перевищенні — 503/429 з `Connection: close`;
    - зменшити типовий JSON-ліміт (близько 100 КБ) з підвищенням на рівні маршруту;
    - `rateLimit` на admin-групу бази знань або на маршрут завантаження;
    - для multipart-маршрутів за `session_web` — дешева синхронна перевірка наявності підписаної session cookie до читання тіла.

### M-4. Немає ліміту одночасних WebSocket-з'єднань на користувача чи IP

- **Де:**
    - `vendor/utils/rate-limit/ws-message-budget.ts` — бюджет зберігається в `userData.messageBudget`, тобто на сокет;
    - `app/websocket/ws-connection-registry.ts:43-70` — немає обмеження на кількість з'єднань;
    - `app/websocket/ws-session-auth.ts:23` — токен читається через `redis.get`, тож придатний для багатьох з'єднань;
    - `vendor/utils/routing/ws-api-dispatcher.ts:54-58` — per-route ліміт діє лише для відомих маршрутів.
- **Сценарій:**
    1. Один автентифікований акаунт з одного IP відкриває сокети на межі ліміту upgrade (60/хв спільний, 120/хв локальний) і тримає їх. Одного токена досить для всіх, бо ping продовжує його TTL.
    2. За ~10 хвилин накопичується близько 600 сокетів.
    3. Кожен шле 120 повідомлень/хв з невідомою подією (наприклад `x:y`), яка оминає per-route ліміт.
- **Наслідок:** кожне таке повідомлення коштує `EXPIRE` і `GET` у Redis та запиту `findSessionToken` до пулу перевірки сесій, спільного з HTTP (5 з'єднань). Це близько 1200 перевірок сесії на секунду від одного користувача; HTTP-перевірки сесій для всіх почнуть завершуватися 503. Кожен сокет також додає рядок `user_online` і пам'ять реєстру без межі.
- **Звірено:** частково. Відсутність ліміту й область дії бюджету підтверджено. Вичерпання пулу не перевірено навантаженням; у доказах feat-149 воно теж позначене як неперевірене.
- **Стан:** feat-149 (рішення Д2) обрала лише «бюджет на з'єднання»; ліміту з'єднань немає ні в документах, ні в `feature_list.json`.
- **Виправлення:**
    - ліміт одночасних з'єднань на користувача (близько 10) і на IP у `handleUpgrade`/`handleConnected` — відмова 429 або закриття найстарішого;
    - за бажанням — бюджет повідомлень на користувача, а не на сокет;
    - одноразовий токен через `GETDEL` (див. L-12).

## Низькі

### Автентифікація, пошта, SMS

#### L-1. Довільний текст у `name` потрапляє в лист на чужу непідтверджену адресу

- **Де:** `packages/shared/src/schemas/auth/register-email.ts:5` (`name: 'string >= 1 & string <= 100'`, без обмеження символів); `app/services/notifications/email-templates.ts:62-70`; `app/services/auth/email-verification-service.ts:166, 440`; `app/services/auth/oauth-service.ts:686-691` (ім'я профілю провайдера в `intro`).
- **Сценарій:** анонім надсилає `POST /api/auth/register/email` з `email` жертви та `name` на кшталт «your account is locked. Sign in at https://evil.example/x». Жертва отримує справжній, коректно підписаний лист «Confirm your email», що починається з тексту зловмисника.
- **Наслідок:** фішинг від домену продукту; акаунт не компрометується. HTML екранується (feat-108), але поштові клієнти роблять URL клікабельними, а текстова частина пропускає й переноси рядків. Ті самі точки входу: `link-email/start` для автентифікованого phone-only акаунта і лист прив'язки OAuth.
- **Обмеження:** `registerEmailIp` 10/год на IP, `registerEmailIdentifier` 3/год на адресу.
- **Звірено:** так (шлях `name` → привітання). Для OAuth-варіанта не перевірено, чи обмежено довжину `providerName` вище за потоком.
- **Виправлення:** не вставляти ім'я в листи на ще не підтверджені адреси; або обмежити `name` у схемі (без `/`, `:`, `@`, керівних символів і переносів). Так само обрізати й нейтралізувати `providerName`.

#### L-2. Повторний лист підтвердження при вході без добового ліміту

- **Де:** `app/services/auth/auth-service.ts:996-1003, 324-335`; `config/throttle-policies.ts:170-175` (`loginUnverifiedResend`: 1 раз на 5 хв на акаунт, без загального ліміту).
- **Сценарій:** у strict-режимі (типовому) анонім реєструє адресу жертви зі своїм паролем і входить з ним кожні 5 хвилин.
- **Наслідок:** 12 листів/год (288/добу) на чужу адресу, доки акаунт не підтверджено; кожен несе ім'я з L-1. 12 входів на годину значно нижче `loginIp` і `loginIdentifier`. Явний endpoint повторного надсилання обмежений 3/год, цей шлях — ні.
- **Звірено:** так.
- **Виправлення:** спільний з `resendVerificationUser` годинний і добовий ліміт (наприклад 3/год і близько 5/добу на акаунт); або видалення ніколи не підтверджених акаунтів після TTL.

#### L-3. Блокування скидання пароля за телефоном сторонньою особою

- **Де:** `app/services/auth/password-reset-service.ts:234-253`; `config/auth.ts:20` (`smsSendPhone` 3/год на номер, спільний для всіх SMS-потоків); TTL challenge 10 хв.
- **Сценарій:** анонім, що знає номер жертви, викликає `reset-phone/start` у моменти t=0, ≈10 і ≈20 хв.
- **Наслідок:** поки живий challenge зловмисника, власник на свій start отримує загальну відповідь без `challengeId`. SMS-коди він отримує, але скористатися ними не може: `reset-phone/complete` вимагає `challengeId`, який був лише у відповіді зловмисникові. Після третього надсилання годинний бюджет вичерпано, і власник до кінця години отримує 429. Для phone-only акаунтів це єдиний спосіб відновлення. Те саме вичерпання бюджету через `register/phone/start` блокує реєстрацію і link-phone для номера.
- **Звірено:** так.
- **Стан:** feat-160 свідомо обрала цю поведінку, щоб закрити зворотну атаку (скасування чужого скидання); наслідок «виграє той, хто почав перший» як прийнятий ризик не записаний.
- **Виправлення:** дозволити другій сесії відкрити власний паралельний challenge (не більше N живих на номер); або рахувати SMS-бюджет окремо для запитів з іншої сесії чи IP; щонайменше — задокументувати як прийнятий ризик.

#### L-4. Немає довгого ліміту помилкових SMS-кодів; різниця в часі відповіді

Обидві частини актуальні лише з реальним SMS-провайдером, якого шаблон не постачає (`UnsupportedSmsVerificationProvider`).

- **а) Бюджет вгадування** — `config/auth.ts:14, 20`; `app/services/auth/sms-challenge.ts:157-181`. Ліміт на один challenge атомарний і надійний, але зловмисник може почати скидання для phone-only акаунта і мати 5 спроб на challenge, 3 challenge на годину: 15 спроб/год, близько 360/добу на номер безстроково. Для 6-значного коду це ≈0,036 % на ціль за добу. Успіх означає повне захоплення акаунта.
    - **Виправлення:** лічильник невдалих підтверджень на номер з довгим вікном (наприклад 10 помилок за 24 год блокують скидання для номера); вимагати від провайдера щонайменше 6 цифр.
- **б) Різниця в часі** — `app/services/auth/password-reset-service.ts:282-309`. Для відомого phone-only номера чекається `issueSmsChallenge` (мережевий виклик провайдера), для невідомого — лише `openChallenge`. Тіло відповіді однакове, але з реальним провайдером затримка видасть, які номери є phone-only акаунтами.
    - **Виправлення:** надсилати у фоні після відповіді, як це робить скидання через пошту.
- **Звірено:** частково (пункт б — так; пункт а взято з первинного огляду).

#### L-5. `.env.example` вимикає `__Host-`, старт у production-режимі це приймає

- **Де:** `packages/backend/.env.example:137` (`SESSION_COOKIE_HOST_PREFIX=false`); `config/session.ts:13` (явне `false` перемагає типове значення для production); `config/session.ts:73` (`secure` читає сирий `APP_ENV`, незалежно від `isProductionLike`); `app/start/validate-runtime-config.ts:143-152` (перевірка лише коли префікс увімкнено); `vendor/utils/network/http-request-handlers.ts:286` (при дублях cookie перемагає остання).
- **Сценарій:** оператор копіює `.env.example` і ставить `APP_IS_PRODUCTION=true`. Cookie лишається `uapi`; якщо `APP_ENV` залишено `local`, вона ще й без `Secure`. Сервер стартує без попередження, хоча документація каже, що префікс у production увімкнено за замовчуванням. Зловмисник, що контролює сусідній піддомен, ставить власну валідну cookie `uapi` з `Domain=<батьківський>`.
- **Наслідок:** браузер жертви працює в сесії зловмисника, і введені дані потрапляють у його акаунт. Підроблені cross-origin POST з піддомену все одно зупиняє allowlist Origin, а вхід ротує id сесії.
- **Звірено:** так. Порядок cookie в браузері — стандартна поведінка, тут не тестувалася.
- **Виправлення:** прибрати або закоментувати рядок у `.env.example` (compose і так задає його для local); у `validateRuntimeConfig` кидати помилку або попереджати, коли `isProductionLike` і cookie без `Secure` чи без префікса.

### OAuth

#### L-6. `GET /auth/oauth/:provider/redirect` запускає вхід без підтвердження наміру

- **Де:** `app/routes/http-routes.ts:156-160`; `app/controllers/http/auth/oauth-controller.ts:84-114`; `app/middlewares/csrf-guard.ts:106-109` (GET пропускає всі перевірки).

- **Звірено:** частково. Код підтверджено; тихе завершення залежить від поведінки провайдера, наживо не тестувалося.

#### L-7. State не прив'язаний до провайдера; PKCE лише для Google

- **Звірено:** так.
- **Виправлення:** зберігати `oauthProvider` разом зі state і додати його до очікуваного набору в `consumeSessionData`; надсилати PKCE challenge для GitLab і GitHub.

- **Виправлення:** вважати відсутній або `false` `email_verified` відсутністю email і повертати наявну помилку «Could not retrieve email from provider».

#### L-9. `providerName` і `providerAvatar` не обрізаються під розмір колонок

### WebSocket

#### L-11. Бінарні фрейми оминають бюджет повідомлень

- **Де:** `vendor/utils/network/ws-handlers.ts:306-309`.
- **Суть:** перевірка `isBinary` з `logger.error` стоїть перед створенням і перевіркою бюджету.
- **Наслідок:** автентифікований клієнт шле бінарні фрейми (до 1 МБ) з максимальною швидкістю; вони не рахуються, не відхиляються і не спричиняють закриття 4029. Кожен дає рядок рівня `error` — навантаження на диск і шум, що глушить алерти.

#### L-12. WS-токен не одноразовий, усупереч документації

- **Де:** `app/websocket/ws-session-auth.ts:23` (`redis.get`, а не `getdel`); `:104-107` (кожне повідомлення і ping скидає TTL до 120 с); `vendor/utils/network/ws-handlers.ts:735` (токен повертається в заголовку `Sec-WebSocket-Protocol`); `documentation/backend/websocket.md` стверджує, що токен одноразовий щодо з'єднання.

- **Звірено:** так.
- **Виправлення:** `GETDEL` при upgrade, а sessionId і userToken тримати лише в `userData`. Тоді `onRefreshToken` і `onRevokeToken` стають зайвими, що прибирає команду Redis на кожне повідомлення.

#### L-13. Per-route ліміт ключується лише за IP

- **Де:** `vendor/utils/rate-limit/ws-rate-limit.ts:43`.
- **Наслідок:** користувачі за одним NAT ділять бюджети 60/хв для `support/*` і 120/хв для `admin/*`, тож один може вичерпати їх для інших. І навпаки: один користувач на кількох IP множить свій ліміт. Чат підтримки має окремий per-user контроль у `supportService`, тому вплив малий.
- **Звірено:** ні.
- **Виправлення:** ключ за `userData.userId` (завжди наявний на сокеті), за бажанням разом з IP.

### HTTP-ядро

#### L-14. Запис у лог на кожен невалідний заголовок до rate limit

- **Де:** `vendor/utils/network/http-request-handlers.ts:62-66` (викликається з `collectRequestMetadata`, `server.ts:488`, до лімітера на `:498`); `vendor/utils/rate-limit/http-rate-limit.ts:76`.
- **Суть:** на кожен невалідний заголовок (будь-який байт понад 0x7E у значенні) пишеться рядок `warn` — і для запитів, що потім отримують 429. Кожен відхилений запит ще й пише власний `Rate limit exceeded`.
- **Наслідок:** навантаження на диск і конвеєр логів, шум, що ховає справжні події. Ін'єкції в лог немає: pino екранує ім'я.
- **Звірено:** частково. Порядок підтверджено; коефіцієнт підсилення залежить від ліміту кількості заголовків у uWS, який не перевірявся.
- **Виправлення:** не більше одного агрегованого рядка на запит (лічильник, рівень `debug`); обмежити частоту `Rate limit exceeded` на ключ.

#### L-15. HTML, що віддається з диска, не отримує CSP

- **Де:** `vendor/start/static-server.ts:210-213, 372-378, 405-407`.
- **Суть:** `.html`/`.htm` файл понад `STATIC_MAX_MEMORY_FILE_SIZE` (1 МіБ) або будь-який HTML після вичерпання 64 МіБ бюджету пам'яті стає `disk`-записом і віддається з `cspKind = null`, тобто без `Content-Security-Policy`.
- **Наслідок:** лише прогалина в захисті в глибину (статика — це результат збірки). `index.html` завжди в пам'яті й не зачеплений; інші security-заголовки надсилаються.
- **Звірено:** так.
- **Виправлення:** `getAssetCspKind` має повертати `'document'` для `html`/`htm`, або примусово тримати HTML у пам'яті.

#### L-16. Ключ per-route ліміту не містить методу

- **Де:** `vendor/utils/rate-limit/http-rate-limit.ts:122`; `vendor/utils/rate-limit/rate-limit-store.ts:109-112`.
- **Суть:** два маршрути з однаковим URL і різними методами ділять один sliding log, і кожен виклик перезаписує `existing.windowMs`.
- **Наслідок:** це не обхід: лічильники додаються. Але дешеві запити до м'якшого маршруту можуть заблокувати суворіший для того самого IP. Чи є зараз пари маршрутів з різними лімітами — не перевірено.
- **Звірено:** так.
- **Виправлення:** додати `route.method` у ключ.

### Фронтенд та інфраструктура

#### L-17. Session Replay надсилає URL з одноразовим токеном у Sentry

- **Де:** `packages/frontend/src/utils/sentry-service.ts:220-225`; `packages/frontend/src/views/ResetPasswordView.vue:27-30`, `VerifyEmailView.vue:27`, `OAuthLinkConfirmView.vue:27` (токен читається з `route.query.token` і лишається в адресному рядку).
- **Суть:** Replay записує повний URL разом із query. Подія replay проходить лише event processors; хуки `beforeSend`, `beforeBreadcrumb` і `beforeSendSpan`, що виконують маскування (feat-194), для неї не викликаються, а `beforeAddRecordingEvent` не налаштовано.
- **Сценарій:** зловмисник має доступ на читання до проєкту Sentry. Користувач відкриває `/reset-password?token=…`; replay відправляється за секунди, до надсилання форми. Зловмисник читає токен і скидає пароль першим.
- **Передумова:** `VITE_SENTRY_REPLAYS_*_SAMPLE_RATE > 0`. У `.env.example` значення порожні, тобто це вмикається свідомо.
- **Звірено:** частково. Конфігурацію застосунку підтверджено; шлях усередині `@sentry/replay@11.10.0` взято з первинного огляду.
- **Виправлення:** `beforeAddRecordingEvent`, що маскує `data.href` і URL у `data.payload` наявним `maskUrl`; event processor для `event.type === 'replay_event'`, що маскує `urls` і `request.url`; за можливості — `router.replace`, щоб прибрати `token` з URL після читання в пам'ять.

#### L-18. Базовий образ без digest і `curl | bash`

- **Де:** `Dockerfile:4, 12` (builder) і `:75, 83` (production).
- **Суть:** `FROM ubuntu:24.04` за плаваючим тегом; Node ставиться через `curl -fsSL https://deb.nodesource.com/setup_24.x | bash -`. Єдина перевірка — `node -v`, яка фіксує рядок версії, а не вміст. `curl` лишається в runtime-образі (його використовує HEALTHCHECK).
- **Наслідок:** скомпрометований чи змінений скрипт NodeSource або перетегований базовий образ виконується від root у фінальній стадії.
- **Звірено:** так.
- **Стан:** `docker-hardening-plan.md` згадує NodeSource і `ubuntu:24.04` як факти, але пункту про закріплення digest немає.
- **Виправлення:** `ubuntu:24.04@sha256:…` або офіційний `node:24.22.2-slim@sha256:…`; або явно встановлювати apt-ключ і репозиторій NodeSource.

#### L-19. Lifecycle-скрипти залежностей не обмежені; advisories ніхто не відстежує

- **Де:** кореневий `package.json` (`"packageManager": "pnpm@9.15.0"`, без `pnpm.onlyBuiltDependencies`, без `.npmrc`); `.github/dependabot.yml` (лише `github-actions`); жоден workflow не запускає `pnpm audit`.
- **Суть:** pnpm 9 виконує `preinstall`/`install`/`postinstall` кожної залежності — у CI і від root в обох стадіях Dockerfile. Зараз такий скрипт має лише `esbuild`.
- **Наслідок:** нову advisory або шкідливий транзитивний реліз помітить лише ручний аудит.
- **Звірено:** так.
- **Виправлення:** `"onlyBuiltDependencies": ["esbuild"]`; екосистема `npm` у dependabot або запланований `pnpm audit --prod`.

## Інформаційні

Дій не вимагають; зафіксовано, щоб не відкривати повторно.

- **I-1. Історія чату вставляється в prompt одним текстом** (`app/services/support/support-llm-service.ts:101-106`). Користувач може підробити репліки `assistant:`, але лише у власній розмові. Виклики підтримки не передають інструментів, а контекст містить тільки активні статті бази знань. Найгірший наслідок — користувач дістане системний prompt і текст активних статей; обидва варто вважати доступними користувачеві й не тримати в них секретів.
- **I-2. `users.avatar` від OAuth-провайдера зберігається без перевірки.** `deleteAvatarObject` (`app/services/user/avatar-service.ts:57-61`) пропускає лише значення, що відповідають `^https?://`. Провайдер, який повернув би не-URL, спричинив би `DeleteObject` на `<prefix>/uploads/<цей рядок>`. Поточні провайдери повертають абсолютні URL; перевірка на `https://` при отриманні закрила б питання.
- **I-3. Відповіді списку й читання push-підписок повертають власнику `p256dhKey`, `authKey` і `ipAddress`** (`packages/shared/src/responses/push-subscription-controller.ts:13-16`). Міжкористувацького витоку немає, але клієнту ключі назад не потрібні.
- **I-4. `uWebSockets.js` у lock-файлі без integrity-хеша** (`pnpm-lock.yaml:4519`, tarball з codeload.github.com). Закріплено за SHA коміту, тож ризик малий, але це єдина нативна мережева залежність без хеша вмісту.
- **I-5. `public-test` копіюється в production-образ** (`Dockerfile:124`). Віддається лише при `APP_ENV=manual-test`; у звичайному розгортанні недосяжний. Прибрати COPY — і питання зникає.
- **I-6. `dompurify` оголошено в `packages/frontend/package.json`, але ніде не імпортується.**
- **I-7. `PASSWORD_MAX_LENGTH = 32`** (`packages/shared/src/limits/index.ts:19`) відсікає довгі паролі з менеджерів; 64–128 зі scrypt безпечно.

## Перевірено й тримається

- **Авторизація маршрутів:** IDOR чи пропущених admin-перевірок немає; кожен не-GET маршрут стоїть за `session_web` + `csrf_guard`; роль адміна перечитується з БД на кожен запит.
- **Сесії:** id з `crypto.randomUUID()`, cookie з HMAC-SHA256 і порівнянням за сталий час; ротація id при вході; відкликання за ADR 0002 без fail-open (збій БД дає 503).
- **CSRF і CORS:** токен прив'язаний до сесії; Origin — точний збіг з allowlist, `null` відхиляється; CORS без wildcard, з `Vary: Origin`.
- **Одноразові токени:** `randomBytes(32)`, зберігаються лише як SHA-256, споживаються одним атомарним `UPDATE`; посилання будуються з `appConfig.frontendUrl`, а не з Host.
- **Вхід:** ліміти споживаються до пошуку користувача; для невідомих акаунтів scrypt виконується над фіктивним хешем; усі відмови дають однаковий 401.
- **OAuth:** state одноразовий, зберігається на сервері, споживається Lua compare-and-set; ключ ідентичності — `(provider, provider_user_id)`; захист від pre-hijack (feat-097/098) тримається в обох напрямках; `redirect_uri` лише з env.
- **Ін'єкції:** SQL — лише параметризовані фрагменти Drizzle, включно з pgvector; у фронтенді немає `v-html`, `innerHTML`, `document.write`; open redirect закрито `safe-redirect.ts`.
- **SSRF і завантаження:** push endpoint — https, типовий порт, без userinfo та IP-літералів, allowlist хостів, без редиректів; аватари — перевірка magic bytes, лише jpeg/png/webp, ключ генерує сервер.
- **Витрати LLM:** лише для автентифікованих; per-user ліміти; добове резервування атомарним Lua-скриптом з fail-closed.
- **Мережевий шар:** IP визначається обходом `X-Forwarded-For` справа наліво лише через довірені CIDR; rate limit fail-closed; ліміт тіла діє під час стримінгу; захист від prototype pollution; статика не передає URL у файлову систему.
- **Логи й помилки:** сирий заголовок `cookie` не потрапляє в мапу заголовків; query string не логується; текст внутрішніх помилок віддається лише при `APP_ENV=local`.
- **Патч `uWebSockets.js@20.71.0`:** однорядкове виправлення шляху імпорту в `ESM_wrapper.mjs`, без зміни поведінки.
- **CI та репозиторій:** Actions закріплені за SHA, `permissions: contents: read`, немає `pull_request_target`; порти compose на `127.0.0.1`; `.dockerignore` виключає `.env*`; секретів у відстежуваних файлах немає.
