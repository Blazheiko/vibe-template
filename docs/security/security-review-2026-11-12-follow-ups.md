## 1. Dependabot пропонує змінити тег базового образу

Після feat-207 (#631) у `.github/dependabot.yml` є екосистема `docker`. Задум — щоб Dependabot оновлював digest у `FROM ubuntu:24.04@sha256:…`. Натомість він одразу відкрив PR #633 «Bump ubuntu from 24.04 to 25.10», тобто пропонує змінити сам тег.

Зливати його не слід: 25.10 — не LTS, а рішення Д7 плану лишає `ubuntu:24.04`. Крім того, образ із новим випуском треба заново перевіряти з `uWebSockets.js` і пакетом NodeSource.

Що зробити:

- закрити PR #633;
- додати до запису `docker` у `dependabot.yml` правило, яке лишає тільки оновлення digest:

    ```yaml
    ignore:
        - dependency-name: ubuntu
          update-types: ['version-update:semver-major', 'version-update:semver-minor']
    ```

- після цього переконатися на наступному запуску Dependabot, що PR на зміну тегу більше не з'являються, а PR на новий digest — з'являються. Чи відкриває Dependabot окремі PR лише на digest за такого правила, не перевірено.

## 2. Advisory у `hono` та `@hono/node-server`

`pnpm audit --prod` станом на 2026-11-13 показує 6 moderate і 1 low:

| Пакет               | Вразливі версії  | Виправлено в |
| ------------------- | ---------------- | ------------ |
| `hono`              | `<4.13.16`       | `4.13.16`    |
| `@hono/node-server` | `>=2.0.0 <2.1.6` | `2.1.6`      |

Обидва пакети приходять лише транзитивно: `packages/backend` → `@mistralai/mistralai@3.4.0` → `@modelcontextprotocol/sdk@1.32.2` → `hono` / `@hono/node-server`. На момент рев'ю (2026-11-12) `pnpm audit` вразливостей не показував.

Чи досяжний цей код у рантаймі шаблону, не перевірено: бекенд використовує з Mistral SDK лише клієнт чату, а `hono` потрібен серверній частині MCP SDK.

Що зробити: оновити `@mistralai/mistralai`, якщо нова версія тягне виправлені пакети, або додати `hono` і `@hono/node-server` у `pnpm.overrides` кореневого `package.json`. Тижневий `audit.yml` через ці advisory не падає: його поріг — high.

## 3. `audit.yml` ще не запускався в GitHub Actions

Workflow `.github/workflows/audit.yml` (feat-207) запускається за розкладом (понеділок, 05:17 UTC) і вручну. На PR він не виконується, тому в CI його ще ніхто не бачив. Обидві його команди (`pnpm audit --prod` і `pnpm audit --prod --audit-level=high`) запускалися локально й відпрацювали.

Що зробити: запустити його один раз вручну (`gh workflow run audit.yml` або кнопка «Run workflow») і переконатися, що job зелений.

## 4. Налаштування «Dependabot security updates»

Екосистема `npm` у `dependabot.yml` має `open-pull-requests-limit: 0`: оновлення версій вимкнено навмисно (TypeScript, drizzle rc та інші закріплені), лишаються тільки PR на вразливі пакети. Такі PR Dependabot відкриває, лише коли в налаштуваннях репозиторію (Settings → Advanced Security) увімкнено «Dependabot security updates». Чи увімкнено — не перевірялося.

Без цього налаштування про нові advisory повідомлятиме лише тижневий `audit.yml` (пункт 3).

## 5. OAuth не перевірено на справжніх провайдерах

feat-200 (#610) змінив потік OAuth: відмова на `Sec-Fetch-Site: cross-site`, прив'язка state до провайдера, PKCE S256 для GitHub і GitLab, для GitLab — лише адреса з `email_verified: true`. Усе це перевірено тестами з підставним клієнтом провайдера. На справжніх Google, GitHub і GitLab вхід не запускався: потрібні облікові дані застосунків.

Що зробити: перед першим розгортанням пройти вхід і прив'язку через кожного ввімкненого провайдера. Найбільший ризик — PKCE для GitHub і GitLab та відмова GitLab для адреси без `email_verified`.

## 6. L-14: розбіжність зі звітом

Звіт стверджує, що невалідним вважається «будь-який байт понад 0x7E у значенні» заголовка. На живому стеку запит із заголовком `x-utf: café` пройшов без запису про відхилений заголовок; невалідне ім'я (`x.bad`) відхиляється, як і очікувалося. Виправлення L-14 (один рядок `debug` на запит) від цього не залежить.

Чому значення з UTF-8 проходить перевірку `HEADER_VALUE_PATTERN` у `app/validate/checkers/header-checker.ts`, не з'ясовано. Можливі причини: uWebSockets.js віддає значення в іншому вигляді, ніж очікує шаблон, або `curl` змінює його перед відправкою. Варто перевірити окремим тестом на справжньому сервері.

**З'ясовано feat-215** (2026-11-13): тест на справжньому uWebSockets.js із сирим запитом через сокет показав, що uWS обрізає байти понад 0x7F на краях значення, як пробіли: `café` надходить як `caf`, `écafe` як `cafe`, `éé` як порожній рядок. Тому `x-utf: café` перевірку проходив. Значення з таким байтом усередині (`caféXYZ`) доходить до `getHeaders` і відхиляється з рядком `debug`. Отже, жоден байт понад 0x7E до застосунку не доходить, і код змінювати не потрібно. Обидві поведінки зафіксовано в `vendor/utils/network/header-values.live.spec.ts`, тож оновлення uWS, яке їх змінить, цей тест помітить.

Принагідно: uWebSockets.js сам відповідає 400 на запит, у якому більше ніж приблизно 100 заголовків або є керівний символ у значенні.

## 7. Нестабільний mock e2e-тест

`packages/frontend/e2e/mock/login.spec.ts:153` («a second click while the request is in flight sends nothing: one request») один раз упав під час повного локального запуску feat-208: кнопка «Signing In...» зникла раніше, ніж тест устиг узяти її координати. Окремо тест пройшов тричі поспіль, у повторному повному запуску і в CI — теж. Змін feat-208 він не стосується.

Що зробити: якщо впаде в CI, подовжити затримку відповіді в моку цього тесту, щоб стан «запит у дорозі» тривав довше.

## 8. SMS-бюджет у реєстрації та прив'язці телефону

feat-212 переніс списання годинного SMS-бюджету номера під advisory-блокування лише для скидання пароля за телефоном (`reset-phone/start`): там платить тільки старт, що справді відкриває челендж.

Два інші потоки, `register/phone/start` і `link-phone/start` (`auth-service.ts`), списують `smsSendPhone` ще до перевірки cooldown. Тож старт, відхилений через cooldown, бюджет витрачає — і послідовно, і пачкою паралельних запитів. Наслідок той самий, що описано для скидання: бюджет чужого номера можна вичерпати, не надіславши жодного SMS, і власник годину не зможе зареєструватися чи прив'язати цей номер. Для `link-phone` це додатково обмежує бюджет на акаунт (`linkPhoneUser`), для реєстрації — лише бюджет на IP.

Це поведінка, що існувала до рев'ю; у звіті й у зауваженнях повторної перевірки її немає, тому в feat-212 вона не змінювалася. Механізм для виправлення вже є: параметр `spendBudget` можна додати до `openChallenge` так само, як до `openSessionChallenge`.

**Виправлено feat-214** (2026-11-13): `openChallenge` приймає `spendBudget` і викликає його під advisory-блокуванням після перевірки cooldown; обидва потоки передають туди `smsSendPhone`. Ліміти на IP і на акаунт лишилися до блокування. PG-тест `register-link-phone-sms-budget.pg.test.ts` на старому коді: 8 паралельних стартів списували 8 одиниць, тепер 1.
