# Roles and capabilities

The matrix shows what each role can do and **how exactly this is enforced in the code**. The basis is [`docs/reference/template-role-capability-matrix.md`](https://github.com/Blazheiko/vibe-template/blob/main/docs/reference/template-role-capability-matrix.md). Each row was checked against [`http-routes.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/http-routes.ts), [`ws-routes.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/ws-routes.ts), the independent table in [`route-permissions.spec.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/route-permissions.spec.ts) and the frontend router [`router/index.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/router/index.ts).

## How a role is determined

- **Anonymous**: there is no valid session, `context.auth.getUserId()` returns `null`.
- **Authenticated user**: the session was restored by `session_web`. [`auth-guard.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/middlewares/core/auth-guard.ts) returns `401` if `auth.check()` is false.
- **Role**: a user has one: the `users.role` column, the pg enum `user_role` (`user`, `support_operator`, `kb_editor`, `user_admin`, `admin`, default `user`). What a role may do is computed by code from the closed catalog [`shared/src/access/index.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/access/index.ts) (`ROLES`, `PERMISSIONS`, `ROLE_DEFINITIONS`, `roleHasPermission`, `canAssignRole`, `isStaffRole`); permissions are not read from the DB.
- **HTTP**: an admin route has `can:<permission>` after `auth_guard`. [`permission-guard.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/middlewares/permission-guard.ts) reads the role from the DB on every request (a role change applies from the next request) and without the permission answers the canonical `403 {"status":"error","code":"forbidden","message":"Access denied"}`, the same for every permission.
- **WebSocket**: `ws_can:<permission>` ([`ws-permission-guard.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/middlewares/ws-permission-guard.ts)) takes the role of the connection (`userData.role`), which [role sync](/en/backend/websocket#role-sync) keeps in step with the DB; while the admin channel of the connection is paused, it is also `403`.
- **Frontend** only hides what is unavailable: `can(permission)` and `isStaff()` in [`stores/user.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/stores/user.ts), the admin pages and their permissions in [`admin-pages.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/views/admin/admin-pages.ts), the route meta `requiresStaff` and `permission`. The backend checks every request.
- **Staff role**: a role with at least one permission (`isStaffRole`): every role but `user`. It may open the admin area and needs a verified email: the constraint `users_staff_role_verified_email` (`CHECK (role = 'user' OR email_verified_at IS NOT NULL)`, migration [`20261121131849_users_staff_role_verified_email`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/drizzle/migrations/20261121131849_users_staff_role_verified_email/migration.sql)).
- **Developer/QA** and **Operator** do not exist in the code as roles. These are people with access to the local environment, `.env`, the DB and deployment.

### Role permissions

| Role               | Permissions                                                            | May give and take (`assignableRoles`)   |
| ------------------ | ---------------------------------------------------------------------- | --------------------------------------- |
| `user`             | —                                                                      | —                                       |
| `support_operator` | `users.read`, `audit.read.account`, `kb.read`                          | —                                       |
| `kb_editor`        | `kb.read`, `kb.write`                                                  | —                                       |
| `user_admin`       | `users.read`, `users.roles.assign`, `audit.read`, `audit.read.account` | `user`, `support_operator`, `kb_editor` |
| `admin`            | all (`PERMISSIONS`)                                                    | all roles                               |

`assignableRoles` is the **delegation policy**: which roles the holder of a role may both take away and give. It is explicit and not derived from the permissions: a `user_admin` manages who edits the knowledge base without being able to edit it. `admin` has every permission, so a new permission is at once the administrator's and nobody else's.

### Role change

A role is changed by [`role-assignment-service.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/user/role-assignment-service.ts) under one advisory lock. Rules: no such user — `404`; own role, no `users.roles.assign` or a role outside the delegation policy — `403`; the same role — nothing changes; a staff role for an account without a verified email — `409` with reason `identity_unverified`; the last `admin` keeps the role — `409` with reason `last_admin`; a staff role for an account without a second factor — `409` with reason `mfa_not_enrolled` (feat-247, [staff](/en/backend/mfa#staff)). A change in the admin area needs a fresh proof of the actor (the step-up dialog). The change and the audit event `user.role.changed` commit together; after the commit the instances re-read the role of the user's open connections.

A role is changed in two ways:

- **The admin area.** `PATCH /admin/users/:id/role` with the body `{ "role": "<role>" }` (`can:users.roles.assign`, 30 requests a minute) answers `{ "status": "success", "user": { "id", "role" }, "changed" }`; `changed: false` means the user already had the role. The actor is the user of the request, so the delegation policy applies. In `/admin/users` the "Change role" button is shown only on the rows the delegation policy allows (never the own one), and the dialog offers only the allowed roles and disables the staff roles for an account without a verified email ([`RoleChangeDialog.vue`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/components/admin/RoleChangeDialog.vue)). The user list shows the role and filters by it (`GET /admin/users?role=`).
- **The CLI** `user:set-role` ([Scripts](/en/reference/scripts)): the system actor with source `cli`; the delegation policy does not apply to it, the verified-email, last-administrator and second-factor rules do. The way to give the first roles and to recover when no administrator is left.

There is no separate admin flag: the `is_admin` column was removed by the migration [`20261024171546_drop_users_is_admin`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/drizzle/migrations/20261024171546_drop_users_is_admin/migration.sql), so the single source is `users.role`.

## How to add a role or a permission

1. **Catalog.** Add a permission to `PERMISSIONS` or a role to `ROLES` in [`shared/src/access/index.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/access/index.ts) and describe the role in `ROLE_DEFINITIONS`: its permissions and `assignableRoles`. A role that may give roles has `users.roles.assign`; do not let any role but `admin` give a role that has `users.roles.assign` or `admin`. `admin` gets a new permission automatically.
2. **Enum.** The pg enum `user_role` in [`database/schema.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/database/schema.ts) is built from `ROLES`; for a new role generate a migration (`make db-generate`, `ALTER TYPE "user_role" ADD VALUE …`, as in [`20261121131845_user_role_staff_roles`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/drizzle/migrations/20261121131845_user_role_staff_roles/migration.sql)). A new value cannot be used in the same transaction, so the migration only adds the value. A permission needs no migration.
3. **Routes.** Add `can:<permission>` to the group's `middlewares` after `auth_guard` (`['session_web', 'csrf_guard', 'auth_guard', 'can:kb.write']`), for WS `ws_can:<permission>`. `kernel.ts` creates these middleware for every permission of the catalog; nothing needs registering. Routes with different permissions are separate groups with the same `prefix`.
4. **Matrix test.** Add the route and its permission to the independent tables `HTTP_ROUTE_PERMISSION` / `WS_ROUTE_PERMISSION` and the role's permissions to `ROLE_PERMISSIONS` in [`route-permissions.spec.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/route-permissions.spec.ts). The tables are written by hand, not from the catalog, so the test catches both an unguarded route and excess access.
5. **Menu.** A new admin page is an entry in `ADMIN_PAGES` in [`admin-pages.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/views/admin/admin-pages.ts) and a child route of `/admin` with `meta: { permission }` in the router.
6. **Documentation.** Update the matrix on this page (both locales) and [`template-role-capability-matrix.md`](https://github.com/Blazheiko/vibe-template/blob/main/docs/reference/template-role-capability-matrix.md).

To **remove a role**, deleting it from the catalog is not enough: PostgreSQL cannot drop an enum value, so the `user_role` type has to be recreated by a migration (a new type, moving `users.role` and `audit_events.actor_role` to it, dropping the old one), after changing the role of its holders. The template has no production and no backward compatibility, so this is acceptable.

For more on guards, see [Authentication](/en/backend/auth#roles-and-permissions) and [Middleware](/en/backend/middlewares).
