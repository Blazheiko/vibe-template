# Roles and capabilities

The matrix shows what each role can do and **how exactly this is enforced in the code**. The basis is [`docs/reference/template-role-capability-matrix.md`](https://github.com/Blazheiko/vibe-template/blob/main/docs/reference/template-role-capability-matrix.md). Each row was checked against [`http-routes.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/http-routes.ts), [`ws-routes.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/routes/ws-routes.ts) and the frontend router [`router/index.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/router/index.ts).

## How a role is determined

- **Anonymous**: there is no valid session, `context.auth.getUserId()` returns `null`.
- **Authenticated user**: the session was restored by `session_web`. [`auth-guard.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/middlewares/core/auth-guard.ts) returns `401` if `auth.check()` is false.
- **Admin**: [`admin-guard.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/middlewares/admin-guard.ts) loads the user from the DB and lets the request through only when `user.role === 'admin'` (otherwise `403`). The frontend checks the same field: `isAdmin()` in [`stores/user.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/src/stores/user.ts) returns `user.role === 'admin'`. The WS subscription to the admin channel also checks `userData.role !== "admin"` in [`admin-ws-channel-service.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/admin/admin-ws-channel-service.ts).
- **Developer/QA** and **Operator** do not exist in the code as roles. These are people with access to the local environment, `.env`, the DB and deployment.

There is no separate admin flag: the `is_admin` column was removed by the migration [`20261024171546_drop_users_is_admin`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/drizzle/migrations/20261024171546_drop_users_is_admin/migration.sql), so the single source is `users.role` (`'user' | 'admin'`).

## Matrix

Marks: "Yes", "No", "—" (not applicable). The `session_web` and `csrf_guard` middleware are attached to all groups except `/ping`, so we do not repeat them in the "How it is enforced" column.

| Capability                               | Anonymous | User | Admin | How it is enforced in code                                                                                                                                                                                                                                                                                                                                |
| ---------------------------------------- | --------- | ---- | ----- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Public pages (login, register, policies) | Yes       | Yes  | Yes   | Frontend routes without `meta.requiresAuth` (`/`, `/login`, `/register`, `/verify-email`, `/reset-password`, `/about`, `/privacy-policy`, `/terms`, `/cookies`, `/ai-policy`)                                                                                                                                                                             |
| Registration / sign-in / password reset  | Yes       | —    | —     | The `auth` group: `/register/*`, `/login`, `/forgot-password`, `/reset-password`, `/reset-phone/*`, `/verify-email` without `auth_guard`. Guest routes do not reject already signed-in users: "—" means "not needed", not "forbidden"                                                                                                                     |
| OAuth sign-in                            | Yes       | —    | —     | The `auth/oauth` group: `/:provider/redirect`, `/:provider/callback` without `auth_guard`                                                                                                                                                                                                                                                                 |
| Sign-out, password change                | No        | Yes  | Yes   | `auth_guard` on `/auth/logout`, `/auth/logout-all`, `/auth/change-password`                                                                                                                                                                                                                                                                               |
| Protected app shell                      | No        | Yes  | Yes   | Backend: `auth_guard` on `/main/init`, `/main/update-ws-token`. Frontend: `meta.requiresAuth` on `/account`, `/support`, redirect to `/login`                                                                                                                                                                                                             |
| Linking phone / email                    | No        | Yes  | Yes   | `auth_guard` on `/auth/link-phone/start`, `/auth/link-phone/confirm`, `/auth/link-email/start`, `/auth/resend-verification-email`                                                                                                                                                                                                                         |
| Account / profile update                 | No        | ?    | ?     | There is no dedicated profile update route in `http-routes.ts` (see the warning below)                                                                                                                                                                                                                                                                    |
| Avatar upload / deletion                 | No        | Yes  | Yes   | The `avatar` group with `auth_guard`                                                                                                                                                                                                                                                                                                                      |
| Support chat                             | No        | Yes  | Yes   | HTTP: the `support` group with `auth_guard`. WS: `support_open_chat`, `support_chat` (a WS connection needs a WS token, which is issued only under `auth_guard`)                                                                                                                                                                                          |
| Push subscriptions                       | No        | Yes  | Yes   | The `push-subscriptions` group: `auth_guard` on every route except `vapid-public-key` (available anonymously); the `getUserId()` check in [`push-subscription-controller.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/controllers/http/notifications/push-subscription-controller.ts) remains as an extra safeguard |
| Admin shell                              | No        | No   | Yes   | Frontend: `meta: { requiresAuth: true, requiresAdmin: true }` on `/admin`, a non-admin is redirected to `/account`. Backend: `admin_guard` on all `admin` groups                                                                                                                                                                                          |
| Knowledge base management                | No        | No   | Yes   | `/admin/knowledge-base*` with `auth_guard` + `admin_guard`; UI `/admin/knowledge-base`                                                                                                                                                                                                                                                                    |
| AI prompt management                     | No        | No   | Yes*  | The `prompts` group (`/`, `/:type`, `/:type/test`) with `auth_guard` + `admin_guard`. *There is no prompts page in the frontend router, access only through the API                                                                                                                                                                                       |
| AI usage statistics                      | No        | No   | Yes   | `/admin/usage/text`, `/admin/usage/stats` with `admin_guard`                                                                                                                                                                                                                                                                                              |
| Users and online history                 | No        | No   | Yes   | `/admin/users`, `/admin/users-online*`, `/admin/history-online` with `admin_guard`. The WS group `admin/*` with `ws_admin_guard` (the role from the connection's `userData`); `admin-ws-channel-service` additionally checks `role`                                                                                                                       |
| API playground                           | —         | —    | —     | Does not depend on role. `/doc/routes` is available to anyone, but only with `APP_ENV=manual-test`, `DOC_PAGE=true`, `SERVE_STATIC=true` ([`server.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/start/server.ts)). See [API Playground](/en/playground/)                                                         |
| DB migrations, configuration, deployment | No        | No   | No    | Not HTTP capabilities: CLI scripts (`db:*`, see [Scripts](/en/reference/scripts)) and `.env`. Access is determined by access to the server/repository (Developer/QA locally, Operator in production)                                                                                                                                                      |

::: info Removed route `POST /main/save-user`
The `main` group used to have an anonymous route `/main/save-user` that created a user with an unhashed password (item 65 in the [issues list](https://github.com/Blazheiko/vibe-template/blob/main/docs/plan/code-issues-found-during-docs.md)). It was removed together with the `SaveUserInput`/`SaveUserResponse` schemas, `WSSaveUserPayload` and the client `api.saveUser`. Users are created only through registration (email or phone) and OAuth — see [Authentication](/en/backend/auth#sign-in-methods) and [Social login](/en/backend/oauth).
:::

::: warning Not confirmed
The "Update account/profile" row from the source matrix has no dedicated backend route in `http-routes.ts`. The `/account` page exists, but judging by the routes, only the avatar, phone/email linking and password change work with the profile. The Developer/QA and Operator columns from the source matrix ("Test", "Configure") describe organizational duties and are not enforced by code, so they are not included in the table above.
:::

For more on guards, see [Authentication](/en/backend/auth#roles-auth-guard-and-admin-guard) and [Middleware](/en/backend/middlewares).
