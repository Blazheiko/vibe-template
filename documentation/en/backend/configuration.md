# Configuration

The backend is configured only through environment variables. The defaults and the rules for which variables are required below come from the configuration modules in the code, not from `.env.example`.

## How configuration is loaded

- `.env` is read by [`dotenv`](https://www.npmjs.com/package/dotenv) through `import "dotenv/config"`. This line comes first in the entry point [`src/index.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/index.ts), in [`src/sentry-bootstrap.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/sentry-bootstrap.ts), and in the scripts [`src/db/create-database.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/db/create-database.ts), [`src/db/seed.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/db/seed.ts) and [`src/scripts/send-test-email.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/scripts/send-test-email.ts). The file is looked up in the current working directory of the process, so it is usually `packages/backend/.env`.
- Each file in [`src/config/`](https://github.com/Blazheiko/vibe-template/tree/main/packages/backend/src/config) reads `env` from `node:process` once during import and returns `Object.freeze(...)`. If you change a variable after startup, the process will not see it.
- The PostgreSQL settings are assembled by a single function, `resolveDatabaseConfig()`, in [`src/config/database.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/database.ts). It is used by the application, by `db:create` ([`create-database.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/db/create-database.ts)) and by [`drizzle.config.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/drizzle.config.ts), so the defaults are the same everywhere. [`drizzle.config.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/drizzle.config.ts) does not import `dotenv`.
- Boolean and integer values are parsed by a single pair of functions, [`parseBoolean`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/env/parse-boolean.ts) and [`parseInteger`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/env/read-int.ts), through [`createEnvReader`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/env/env-reader.ts). The rules are in the [Boolean and integer values](#boolean-and-integer-values) section.
- After the configurations are imported, `src/index.ts` calls [`validateRuntimeConfig()`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/start/validate-runtime-config.ts). It throws and stops startup if the combination of variables is invalid. Below, these checks are marked as "throw on startup".

### Boolean and integer values

All boolean and integer variables in `.env` are read by the same code ([`env-reader.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/env/env-reader.ts)). It collects all the problems found in one module and reports them together through `validateRuntimeConfig()` (`Invalid <area> configuration: ...`), with the variable name.

| Type    | Accepted                                                                                                          | Empty / not set        | Any other value                                   |
| ------- | ----------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------------------- |
| boolean | `true`, `1`, `yes`, `on` → true; `false`, `0`, `no`, `off` → false. Case and surrounding whitespace do not matter | the variable's default | startup error (not "false")                       |
| integer | decimal digits, unsigned, within the variable's `{min, max}` (inclusive), a safe integer                          | the variable's default | startup error (`1e3`, `0x10`, `-5`, `1.5`, `5ms`) |

This changed behavior compared with the separate parsers that existed before: `AUTH_PHONE_ENABLED=yes` is now true (previously `auth.ts` only knew `1`/`true`); `True` and `TRUE` are now true everywhere (previously `parseBoolean` was case-sensitive, and `APP_IS_PRODUCTION=True` gave false); a typo in a boolean variable (`CSRF_ENFORCE=flase`) no longer silently gives false but stops startup; `AUTH_*=1e3` and `PORT=abc` are no longer accepted and no longer replaced by the default (previously `PORT` and `SMTP_PORT` silently fell back to `3000`/`587`); an empty value in the rate limit variables is no longer an error but the default. Plain string variables, sizes in bytes (`APP_MAX_BODY_SIZE`, ...), durations (`SESSION_ANON_TTL`) and fractions (`SENTRY_TRACES_SAMPLE_RATE`) have their own rules, described next to the variables.

### Production-like mode

`appConfig.isProductionLike` equals `APP_IS_PRODUCTION` if that variable is set. Otherwise it is true when `APP_ENV` (or `NODE_ENV` if `APP_ENV` is absent), after `trim().toLowerCase()`, is `production` or `prod`. The following depends on this mode:

- The session cookie is named `__Host-uapi` and is always `Secure`, even with `APP_ENV=local`. `APP_URL` must start with `https://`, and `SESSION_COOKIE_HOST_PREFIX=false` is forbidden: startup throws in both cases.
- `AUTH_SMS_PROVIDER=fake` is forbidden: startup throws.

Separately from `isProductionLike`, `APP_ENV` affects other places directly:

- `secure` in cookies ([`cookies.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/cookies.ts), [`session.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/session.ts)) equals `APP_ENV !== 'local'`.
- CSP `connect-src` in [`csp.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/csp.ts) does not allow `ws:` and `http:` when `APP_ENV` is `production` or `prod`. The comparison here is exact, without normalization.

### One source for the API address and prefix

`PORT`, `HOST` and `API_PATH_PREFIX` are set for the backend only: in the shell or in `packages/backend/.env`. The frontend and the API playground keep no copies of these values; their Vite configs read the same variables in the same order as the backend:

1. the shell environment variable (dotenv does not overwrite variables that are already set, so the shell wins);
2. `packages/backend/.env`;
3. the default: `PORT=3000`, `API_PATH_PREFIX=api`; a `HOST` of `0.0.0.0` or `::` (or none) means connecting over `127.0.0.1`.

The backend and the frontend read the value by one rule ([`shared/api-prefix`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/api-prefix/index.ts)): spaces and every outer slash are trimmed (`/v1/` → `v1`), and an empty value or slashes only (`API_PATH_PREFIX=`, `/`) mean `api`. There is no root-level API. [`shared/dev-backend`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/dev-backend/index.ts) resolves them, and they are read by:

| Who                                                                                                                                                                                                                                | What it takes                                                                                    |
| ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------ |
| [`frontend/vite.config.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/vite.config.ts) and [`vite.backend.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/vite.backend.ts) | the dev proxy target `http://<HOST>:<PORT>`, the proxy key `/<prefix>`, the prefix in the bundle |
| [`frontend/vite.sw.config.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/vite.sw.config.ts)                                                                                                           | the prefix whose requests the service worker never caches                                        |
| [`api-playground/vite.config.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/api-playground/vite.config.ts)                                                                                                     | the dev proxy target and key, the prefix in the bundle                                           |
| [`scripts/docker-build.sh`](https://github.com/Blazheiko/vibe-template/blob/main/scripts/docker-build.sh) and `docker-compose.yml`                                                                                                 | the prefix for the image build and for the container ([Deployment](/en/backend/deployment))      |

`VITE_API_PATH_PREFIX` is not a setting but the channel the Vite config uses to hand the prefix to the bundle: the config writes it into `process.env` itself before building. If `VITE_API_PATH_PREFIX` is set by hand (in a frontend `.env*` file or in the shell) and differs from `API_PATH_PREFIX`, `vite`, `vite build` and Vitest fail with `VITE_API_PATH_PREFIX=… differs from the backend API_PATH_PREFIX`. An invalid `PORT` (not an integer from 1 to 65535) stops the Vite config too.

So moving the local backend to another port or prefix takes one edit of `packages/backend/.env` and a restart of `pnpm dev`:

```sh
# packages/backend/.env
PORT=4000
API_PATH_PREFIX=v1
DOMAIN=127.0.0.1:4000
```

`DOMAIN` (the WebSocket address the backend hands to the client) and `APP_URL` / `FRONTEND_URL` stay separate variables: they are public addresses, not the address of the process. A backend on a unix socket (`APP_UNIX_PATH`) is not served by the dev proxy: the proxy connects to `HOST:PORT` only.

## Request body limits

Values are given in bytes: only a positive safe integer written in digits (surrounding whitespace is allowed). Anything else (`abc`, `0`, `-1`, `1.5`, `1e6`, `0x10`, `Infinity`, a number above `Number.MAX_SAFE_INTEGER`) is replaced with the default. The limit per body type is described in [Request lifecycle](/en/backend/request-lifecycle#request-body-types-and-limits).

| Variable                             | Purpose                                                                                                                   | Default               | Required (condition) | Read by file                                                                                      |
| ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- | --------------------- | -------------------- | ------------------------------------------------------------------------------------------------- |
| `APP_MAX_BODY_SIZE`                  | Overall body limit                                                                                                        | `2097152` (2 MiB)     | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_MAX_JSON_BODY_SIZE`             | Limit for JSON                                                                                                            | `2097152` (2 MiB)     | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_DEFAULT_JSON_BODY_SIZE`         | The JSON limit of a route without its own `maxBodySize`; a route may ask for more, up to `APP_MAX_JSON_BODY_SIZE`         | `102400` (100 KB)     | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_MAX_MULTIPART_BODY_SIZE`        | Limit for multipart                                                                                                       | `52428800` (50 MiB)   | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_MAX_OCTET_BODY_SIZE`            | Limit for `application/octet-stream`                                                                                      | `52428800` (50 MiB)   | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_MAX_INFLIGHT_BODY_BYTES`        | How many bytes of request bodies the process buffers at once, in total; over it: `503`; `0` switches it off               | `268435456` (256 MiB) | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |
| `APP_MAX_INFLIGHT_BODY_BYTES_PER_IP` | The same per client address; over it: `429`; `0` switches it off; must not be smaller than the largest body a route takes | `67108864` (64 MiB)   | No                   | [app.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/app.ts) |

Why these defaults:

- **2 MiB for JSON and the remaining types** is the ceiling. A body is read before authentication, so a route without a limit of its own takes only `APP_DEFAULT_JSON_BODY_SIZE` (100 KB, feat-202): real JSON bodies are much smaller. Only routes that say so take more: knowledge base articles (30 000 characters of text) and prompts (50 000). Their limit comes from `jsonBodyLimit` ([upload-limits.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/shared/upload-limits.ts)): 6 bytes per character (the worst case is a character escaped as `\uXXXX`) plus 16 KiB for the other fields. The old reasoning, that lowering the ceiling to 1 MiB would change behavior without any benefit, still holds for the ceiling itself.
- **50 MiB for multipart** is a compatibility policy. The actual need is smaller: the services' file limits are 10 MB for an avatar (`avatar-service.ts`) and 5 MB for a knowledge base screenshot (`knowledge-base-service.ts`), plus a small multipart wrapper. So the body limit can be lowered without affecting existing routes.
- **50 MiB for octet.** The template has no `octet` routes.

When deploying:

- **Proxy.** The limit of the proxy in front of the backend (`client_max_body_size` in nginx, CDN limits) must be at least as large as the body limit you need, otherwise large requests will be cut off by the proxy with its own response, not by the backend with a 413.
- **Memory.** The body is collected in memory, and it is read **before** the session, CSRF and authentication, while the rate limit counts requests, not bytes. So the body buffers have an "in flight" budget of their own (feat-201, [body-budget.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/network/body-budget.ts)): at most `APP_MAX_INFLIGHT_BODY_BYTES` (256 MiB) per process and `APP_MAX_INFLIGHT_BODY_BYTES_PER_IP` (64 MiB) per client address. Bytes are charged chunk by chunk as they arrive and given back when the body is complete, the client goes away or the read fails. A body that takes an address over its limit gets `429`, and when the total is full, `503`; both with `Retry-After: 1` and a closed connection (`Connection: close`), so the rest of the body is not read. Without the budget one address could open hundreds of requests, send almost all of each body and stop. uWS itself closes a stalled request after about 12 s (and one that sends a byte every 5 s as well; measured on uWS 20.71), so the budget bounds the memory inside that window. The counters live in process memory. The estimate of the buffers alone is now `≤ APP_MAX_INFLIGHT_BODY_BYTES × 2` (joining the chunks doubles a body for a moment); it is not an upper bound on process memory: parsers also create strings, objects and copies of data. The per-address limit counts everyone behind one NAT, and behind a reverse proxy without a correct `TRUST_PROXY`, every client at all.

## Redis

## Match with .env.example

[`packages/backend/.env.example`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/.env.example) contains all the variables that the backend reads, except `NODE_ENV` (the fallback source for `APP_ENV`). There are no variables in the file that the code does not read.

- `TURN_SECRET` and `TURN_HOST` are read by [`config/turn.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/config/turn.ts), but nothing imports this module yet.
- The name `CREDENTIONALS_CORS` contains a typo, but that is exactly how the code reads it, so it must not be changed.

To run the project locally, see the [Getting started](/en/guide/getting-started) page. For a general overview of the backend, see the [Backend](/en/backend/) section.
