# Testing

In the monorepo, each package is tested separately: backend and frontend use Vitest, while `shared` and `documentation` use the built-in `node:test`. The root script `pnpm test` runs `pnpm -r test` for all packages ([package.json](https://github.com/Blazheiko/vibe-template/blob/main/package.json)). The main focus below is the backend.

## Backend: Vitest configuration

The config [packages/backend/vitest.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/vitest.config.ts) is minimal:

- `environment: "node"`;
- `exclude`: the default `configDefaults.exclude` plus `dist/**`, `**/*.redis.test.ts` and `**/*.pg.test.ts` (those are run by the separate `test:redis` and `test:pg` scripts, see the "Integration tests with Redis and PostgreSQL" section below). There is no separate `include`, so Vitest picks up the default `*.spec.ts` / `*.test.ts` patterns;
- `testTimeout: 15_000` — 15 s per test instead of the default 5 s: under parallel load (typecheck + lint) 5 s was not enough;
- `maxWorkers` is taken from `VITEST_MAX_WORKERS` if the variable is set (`2` in CI); without it the Vitest default applies;
- the aliases `#app`, `#config`, `#vendor`, `#database`, `#drizzle` point to the corresponding `src/` directories, and `#logger` points to `src/vendor/utils/logger.ts`.

There are no `setupFiles` or `coverage` sections in the config.

Package scripts ([packages/backend/package.json](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/package.json)):

| Script       | Command      |
| ------------ | ------------ |
| `test`       | `vitest run` |
| `test:watch` | `vitest`     |

Tests live next to the code as `*.spec.ts` (for example, `csrf-guard.ts` and `csrf-guard.spec.ts`). An actual run of `pnpm --filter backend test` on the documentation branch gave: **51 files, 268 tests, all passed, ~2.2 s**. Vitest runs each file in a separate worker (isolation by default).

## Mocking patterns

- **Barrel modules.** Services mock `#app/repositories/index.js` and `#app/transformers/index.js`, then dynamically import the service. Details are in [Services](/en/backend/services), [Repositories](/en/backend/repositories) and [Transformers](/en/backend/transformers); a full example is step 9 in [Adding a feature](/en/backend/adding-a-feature).
- **Individual modules.** Some tests mock a specific file, for example `knowledge-base-service.spec.ts` mocks `#app/repositories/support/support-knowledge-repository.js`, `support-embedding-service.js` and `#logger`.
- **Config.** `vi.mock("#config/csrf.js", ...)` in `csrf-guard.spec.ts` substitutes a config with `enforce: true`.
- **uWebSockets.js.** `server.spec.ts` and `http-validation.spec.ts` mock `uWebSockets.js` (`App: () => ({})`), the routes, `ws-handlers` and the HTTP middleware, and replace `HttpResponse` with an object with `vi.fn()` for `cork`/`writeStatus`/`writeHeader`/`end`. A real server does not start and no ports are listened on (there are no `listen(` calls in the spec files).
- **Partial mocks.** `vi.importActual` keeps the rest of the module while replacing one function (`getData` in `http-validation.spec.ts`).

No spec file mocks `#database/db.js` or mentions Redis, so `pnpm --filter backend test` **needs neither a DB nor Redis**.

## Integration tests with Redis and PostgreSQL

| Suffix            | Config                                                                                                                 | Script                             | Variable         | CI                                                                                                        |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------- | ---------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------- |
| `*.redis.test.ts` | [vitest.redis.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/vitest.redis.config.ts) | `pnpm --filter backend test:redis` | `REDIS_TEST_URL` | [redis-tests.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/redis-tests.yml) |
| `*.pg.test.ts`    | [vitest.pg.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/vitest.pg.config.ts)       | `pnpm --filter backend test:pg`    | `PG_TEST_URL`    | [pg-tests.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/pg-tests.yml)       |

Without the variable, all suites are skipped (`describe.skipIf`), so the scripts are safe to run anywhere. Files run sequentially (`fileParallelism: false`).

**PostgreSQL.** Before the tests, [pg-global-setup.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/test-support/pg-global-setup.ts) uses `PG_TEST_URL` (an admin connection, usually to the `postgres` database) to create a temporary database `vibe_test_<random>`, enables `vector`, applies the migrations from `src/drizzle/migrations` into the same `drizzle.__drizzle_migrations` table as `db:migrate`, and points `PGSQL_*` at that database. So `db` from `#database/db.js` and all repositories work against the real schema in tests, without mocks. After the run the database is dropped (`DROP DATABASE … WITH (FORCE)`). An image with pgvector is required — the same `pgvector/pgvector:pg16` as in CI.

Local run:

```bash
docker run -d --rm --name vibe-pg-test -e POSTGRES_PASSWORD=postgres \
  -p 127.0.0.1:55433:5432 pgvector/pgvector:pg16
PG_TEST_URL=postgres://postgres:postgres@127.0.0.1:55433/postgres pnpm --filter backend test:pg
docker stop vibe-pg-test
```

A new pg test: a file `<name>.pg.test.ts` next to the code, `describe.skipIf(!hasPg)` from [pg-test-db.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/test-support/pg-test-db.ts), `#database/db.js` imported dynamically inside `describe`, and `pool.end()` in `afterAll`. Each file creates and cleans up its own test data: the database is shared for the whole run. A sample is [harness.pg.test.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/database/harness.pg.test.ts).

## Coverage

Backend and frontend have a `test:coverage` script (`vitest run --coverage` with the [`@vitest/coverage-v8`](https://vitest.dev/guide/coverage) provider, `text-summary` reports to the console and `html` in `coverage/`):

```bash
pnpm --filter backend test:coverage
pnpm --filter frontend test:coverage
```

There is no threshold: CI only publishes the report. Coverage is counted over the files that tests loaded, not over all of `src/`. Starting values (lines, October 2026): backend ~74%, frontend ~51%.

## Other packages

- **shared** — `"test": "pnpm build && node --test test/*.test.js"` ([package.json](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/package.json)): build first, then `node:test` over [test/languages.test.js](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/test/languages.test.js).
- **frontend** — Vitest in `jsdom` on top of `vite.config`, excluding `e2e/**`, `e2e-csp/**` and `e2e-security/**` ([vitest.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/vitest.config.ts)); unit tests in `src/**/__tests__`. Scripts: `test` (`vitest run`), `test:unit` (`vitest`), `test:e2e` (`playwright test`). Playwright ([playwright.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/playwright.config.ts)) takes tests from `e2e/`, with the projects chromium, firefox, webkit and Mobile Safari, and `webServer` starts `pnpm run dev` on 5173 itself (in CI — `pnpm run preview` on 4173) or reuses one that is already running. Playwright does not start the backend. The fifth project, `mock` (tests in `e2e/mock/`, chromium only), checks the states of the login, registration and password recovery modals against faked API responses: every request to `/api` is served by the test itself via `page.route` (`e2e/mock/support.ts`), and a request without a response fails the test. For it, the config builds a separate copy of the SPA in `dist-e2e-mock/` with `VITE_AUTH_PHONE_ENABLED=true`, `VITE_BASE_URL` pointing at its own origin and Sentry disabled, and serves it via `vite preview` on port 4174, so the result does not depend on the developer's `.env`. The tests pin the current behavior of `AuthModals.vue` as is, including the odd parts (a successful response without a user is shown as an error; Enter in the login field does nothing); their expectations change only deliberately, together with a refactor of that file. A separate config [playwright.live.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/playwright.live.config.ts) with tests in `e2e-live/` (`test:e2e:live`) runs the SPA through a real backend with PostgreSQL (pgvector), Redis and a mail receiver: `e2e-live/mail-sink.ts` is a minimal SMTP server on 2526 to which the backend sends emails (`SMTP_IGNORE_TLS=true`), so the test reads the link from the email the way a user would click it. The script builds the SPA without phone auth from the origin `http://localhost:3100`, and `webServer` first creates the database `vibe_e2e_live` (`db:create`, `db:migrate`, `db:seed --demo`) and only then starts the backend with `CSRF_ENFORCE=true`; the Redis key prefix is new on every run, so the throttle counters of the previous one do not interfere. Each browser in a scenario is a separate `BrowserContext` with its own address in `X-Forwarded-For` (`TRUST_PROXY=true` for localhost only): otherwise they are all 127.0.0.1, and the limit of 10 requests per minute for the `auth` group stops the run. Scenarios: password reset by email, password change on the account page and "log out everywhere" close the sessions of other browsers (the API responds `401`, the page shows the login; the server closes the open WebSocket of a revoked session only on the client's next request, see [WebSocket](/en/backend/websocket)), the old password no longer works, the new one does, the reset link is single-use; registration → email → confirmation → login, where an early login gives the same `401` and a repeated email invalidates the first link; the per-address registration counter is real (the fourth attempt within an hour — `429 rate_limited`, feat-134). PostgreSQL and Redis are required; in CI they are provided by the `e2e-live` job. CSP is checked by a separate config [playwright.csp.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/playwright.csp.config.ts) with tests in `e2e-csp/`: `test:e2e:csp` builds the production static files (`scripts/prod-local.sh --build-only`) and starts the backend twice with `SERVE_STATIC=true` — in enforce and report-only modes. The allowed scenarios are checked: registration, WebSocket (through the end of the handshake — a `pong` frame is expected in response to the heartbeat `ping`), fonts, service worker offline and an image from `CDN_URL` (`naturalWidth > 0`; the CDN role is played by the stub `e2e-csp/cdn-stub.mjs`). Forbidden ones: an inline script (`effectiveDirective` `script-src-elem`), `fetch` outside `connect-src` and an image outside `img-src` to a local probe origin, with a `disposition` check (`enforce` / `report`). PostgreSQL and Redis are required. CSRF and the service worker are checked by [playwright.security.config.ts](https://github.com/Blazheiko/vibe-template/blob/main/packages/frontend/playwright.security.config.ts) with tests in `e2e-security/`: `test:e2e:security` builds the production static files and starts the backend with `CSRF_ENFORCE=true`, `CSRF_STRICT_ORIGIN=true` and `CSRF_ALLOWED_ORIGINS`; `global-setup.ts` creates two demo accounts via `db:seed --demo`. Scenarios: cold login (`init` → `401` → login with a token), logout → login, a stale token with a live session (exactly one retry), a lost session and an account change in another tab (no retry; in the second case, a reload as the new user), rejected mutations with no side effect (foreign `Origin`, `Sec-Fetch-Site: cross-site`, no token, no `Origin`), and no API responses in Cache Storage. The "other tab" is `page.request`, which shares cookies with the browser context. PostgreSQL and Redis are required.

::: warning Not covered
The backend runs with `APP_ENV=local` over http, so the production branch (`upgrade-insecure-requests`, HTTPS/WSS) and real S3/CDN (avatar upload, the `/support/screenshot/:id` redirect) are not checked in the browser tests.
:::

- **documentation** — `node --test "scripts/verify/*.test.mjs"` ([package.json](https://github.com/Blazheiko/vibe-template/blob/main/documentation/package.json)) checks the helpers of the verify-dist script ([lib.test.mjs](https://github.com/Blazheiko/vibe-template/blob/main/documentation/scripts/verify/lib.test.mjs)).

## CI and local run

There are three workflows in `.github/workflows`:

| Workflow                                                                                                  | When                                           | What it does                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [ci.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/ci.yml)                   | every PR and push to `main`, no `paths` filter | job `quality`: `pnpm install --frozen-lockfile` → `pnpm --filter shared build` → `format:check` → `typecheck` → `lint` → `test` → `test:coverage` (artifact `coverage`); job `e2e`: shared build → `pnpm --filter frontend build` → `playwright install --with-deps` (all browsers; `~/.cache/ms-playwright` cached by Playwright version) → `test:e2e` on 5 projects (artifact `playwright-report` on failure); job `e2e-live` (PostgreSQL with pgvector and Redis services): `pnpm --filter frontend test:e2e:live` on chromium (artifact `playwright-live-report` on failure) |
| [pg-tests.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/pg-tests.yml)       | PRs and pushes that change backend/shared      | `pnpm --filter backend test:pg` with a `pgvector/pgvector:pg16` service; the only place where `*.pg.test.ts` run                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| [redis-tests.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/redis-tests.yml) | PRs and pushes that change backend/shared      | `pnpm --filter backend test:redis` with a `redis:7-alpine` service; the only place where `*.redis.test.ts` run                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| [docs.yml](https://github.com/Blazheiko/vibe-template/blob/main/.github/workflows/docs.yml)               | documentation changes                          | `typecheck`, `test`, `docs:build`, `docs:verify` for the `documentation` package and a deploy to GitHub Pages from `main`                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

`shared` is built before the checks because the typecheck and tests of backend/frontend import `shared/dist`. In CI, Playwright runs `pnpm run preview` over the built `dist`, so `frontend build` comes before e2e.

Locally, the same thing, except e2e and coverage, is run by [init.sh](https://github.com/Blazheiko/vibe-template/blob/main/init.sh) (install, typecheck, lint, `pnpm test`, build).

## Recipes

**A service test.** Create `<name>-service.spec.ts` next to the service, mock the repositories barrel and check the `Result`. A ready example is [Adding a feature, step 9](/en/backend/adding-a-feature).

**A route / validation test.** Take `http-validation.spec.ts` as a sample: mock `uWebSockets.js`, `#app/routes/http-routes.js`, `#app/routes/ws-routes.js`, `ws-handlers` and `execute-httpMiddlewares`, declare a route via `defineRawRoute` with an arktype schema (the helper for a route without a contract, allowed only in tests; see [Routing](/en/backend/routing#a-route-without-a-contract-tests-only)) and check that an invalid body gets a 422 response and the handler is not called. For WS, do the same as in `ws-validation.spec.ts`. For schemas, see [Validation](/en/backend/validation).

**Running:**

```bash
pnpm --filter backend test                     # all tests once
pnpm --filter backend test:watch               # watch mode
pnpm --filter backend test csrf-guard          # filter by file path (a vitest argument)
pnpm --filter backend exec vitest run -t "422" # filter by test name (pnpm does not pass the flag through `test -t`)
pnpm --filter frontend test:e2e                # Playwright
pnpm --filter frontend test:e2e:csp            # CSP on the production build through the backend
pnpm --filter frontend test:e2e:security       # CSRF and service worker through the backend with enforce
```

::: warning Gaps

- There are no repository tests yet: the `*.pg.test.ts` infrastructure exists, but apart from a smoke test, the data layer is mocked in tests.
- Coverage has no threshold and covers only the files loaded by tests.

:::
