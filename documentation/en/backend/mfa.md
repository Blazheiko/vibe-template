# Two-step sign-in (MFA)

An account can have a second factor: an authenticator app (TOTP), passkeys (WebAuthn) and one-time recovery codes. A passkey also signs in on its own, without a password. After the password or a social sign-in such an account gets a second-step ticket instead of a session; only the right code creates the session. Sensitive actions (changing the password, linking contacts, removing a sign-in method, managing the factors) are confirmed again (step-up) by one matrix. A recovery code opens a limited recovery session in which the only thing to do is to replace the factor.

Plan and decisions: [`docs/plan/passkeys-mfa-plan.md`](https://github.com/Blazheiko/vibe-template/blob/main/docs/plan/passkeys-mfa-plan.md). Sources: the shared policy [`shared/src/mfa`](https://github.com/Blazheiko/vibe-template/tree/main/packages/shared/src/mfa), the services [`services/auth/mfa`](https://github.com/Blazheiko/vibe-template/tree/main/packages/backend/src/app/services/auth/mfa), the contracts [`contracts/mfa.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/contracts/mfa.ts), [`contracts/passkeys.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/contracts/passkeys.ts) and [`contracts/auth.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/contracts/auth.ts).

## Routes

| ---------------------------------------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |

| `POST /api/auth/mfa/state`               | `session_web`, `csrf_guard`               | whether this browser holds a second step: `{ status: 'mfa_required', methods, completing? }` or `{ status: 'none' }`                                           |

| `POST /api/auth/passkey/verify`          | `session_web`, `csrf_guard`               | a passkey-only sign-in: `{ challengeId, response }`                                                                                                            |
| `POST /api/auth/reauth/options`          | `session_web`, `csrf_guard`, `auth_guard` | the step-up proofs this account can give                                                                                                                       |
| `POST /api/auth/reauth`                  | `session_web`, `csrf_guard`, `auth_guard` | step-up: `{ proof: 'password', password }`, `{ proof: 'totp', code }` or `{ proof: 'webauthn', response }`                                                     |
| `POST /api/auth/reauth/webauthn/options` | `session_web`, `csrf_guard`, `auth_guard` | the options of a passkey step-up (the challenge in this session's data)                                                                                        |
| `POST /api/auth/recovery/finish`         | `session_web`, `csrf_guard`, `auth_guard` | ends the recovery session                                                                                                                                      |
| `GET /api/account/mfa`                   | `session_web`, `csrf_guard`, `auth_guard` | the factors, the codes left, whether a recovery contact exists                                                                                                 |
| `POST /api/account/mfa/totp/setup`       | the same                                  | a new secret (in this session's data, 10 min) and an `otpauth://` URI                                                                                          |
| `POST /api/account/mfa/totp/confirm`     | the same                                  | checks the code and stores the factor; replaces the previous app                                                                                               |
| `DELETE /api/account/mfa/totp`           | the same                                  | turns TOTP off; the last factor takes the recovery codes along                                                                                                 |
| `POST /api/account/mfa/recovery-codes`   | the same                                  | a new batch of codes; the previous one stops working                                                                                                           |
| `GET /api/account/passkeys`              | the same                                  | the account's passkeys (name, type, synced, created, last used)                                                                                                |
| `POST /api/account/passkeys/options`     | the same                                  | the options of a new passkey and an `enrollmentId` (the challenge in this session's data)                                                                      |
| `POST /api/account/passkeys`             | the same                                  | stores the new passkey; idempotent by `enrollmentId`                                                                                                           |
| `PATCH /api/account/passkeys/:id`        | the same                                  | renames a passkey                                                                                                                                              |
| `DELETE /api/account/passkeys/:id`       | the same                                  | removes a passkey; the last way to sign in stays                                                                                                               |

The browser draws the QR code (`qrcode`); the secret never goes to another service.

## The second sign-in step

`POST /api/auth/login` (and the OAuth callback) answers an account with a factor `{ status: 'mfa_required', methods }` (a passkey first when there is one) and sets the ticket cookie `__Host-mfa` (`mfa` without HTTPS): `HttpOnly`, `SameSite=Strict`, 5 min. OAuth redirects to `OAUTH_FRONTEND_MFA_URL` (by default `/login?mfa=required`) with the account's methods: `&methods=webauthn,totp,recovery_code`. The ticket is bound to a cookie of its own, `__Host-mfa_bind` (`mfa_bind` without HTTPS; [`request-session.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/vendor/utils/session/request-session.ts)): a random value, new for every ticket, with the ticket cookie's attributes (`Path=/` whatever `API_PATH_PREFIX` is, `HttpOnly`, `SameSite=Strict`, the same lifetime), set and cleared with it. A stolen ticket cookie opens nothing without it, and the binding does not depend on the session: it outlives the previous session the sign-in deletes.

- Five wrong codes close the ticket. The limit counts confirmed failures, not requests: an infrastructure failure gives the attempt back.
- A failure is counted once per logical attempt ([`mfa-ticket.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/auth/mfa/mfa-ticket.ts)). The form gives every submission of a proof a new `attemptId` (16–64 characters `[A-Za-z0-9_-]`) and sends the same one only with a repeat of the same request; without it every request is an attempt of its own. A repeat of an attempt whose failure was counted gets 401 `invalid_code` with no reservation and no new check; typing the same code again is a new attempt. A Redis failure while counting a failure answers 503 `service_unavailable`, not 401: the repeat with the same `attemptId` counts it or finds it counted. The ticket is deleted at the limit only while it is `open`: a late result of an attempt whose reservation lapsed never deletes a ticket another attempt captured. When a known rollback would take such a ticket back to `open` at the limit, it is deleted instead, and the answer is 401 `mfa_ticket_invalid` with the ticket cookie cleared.
- A TOTP code is spent for one version of the factor (`last_used_step`), so the same code is refused the second time.
- The request that captured the ticket creates the session: first as `pending` before the commit, then in one Redis transition. A repeat of the same request (a lost answer, 503 `mfa_completion_pending`) finishes an already confirmed sign-in with the same session; an unknown `COMMIT` outcome is read with `pg_xact_status`. After that transition the activation runs, in this order, the steps that can fail and are repeated, and only then deletes the browser's previous session: a failure answers 503 `mfa_completion_pending` without the new cookie, and the browser repeats with the cookies and CSRF token it holds, and a repeat whose previous session is gone after all (the activation deleted it before a lost answer) gets 403 `csrf_invalid` first: the client reads `main/init` (a new anonymous session and its CSRF token) and sends the same request again, which the ticket's `mfa_bind` binding still admits. For a previous session of another account the client reloads the page (`account_changed`), and the page-load `POST /auth/mfa/state` of the sign-in page — also on an OAuth return with `?mfa=required` — makes the form send `continue`. What the answer needs (the user) is read before the new session's cookie is issued; after it nothing fails the request: a WebSocket token Redis cannot issue then is left empty (`wsToken: ''`), and `main/init` brings it. Only a failure the repeat can outlive answers so: Redis unavailable, PostgreSQL with no connection, a broken one, a cut wait or a query timeout, the previous session's record left by its lock; any other error (a bug) answers 500 `internal_error`, not an answer the client would repeat for ever. A Redis failure before the ticket is captured (the ticket read, the reservation, the passkey challenge) and a known rollback of the second step's transaction answer a plain 503 `service_unavailable` with `Retry-After`, a PostgreSQL failure there 500 ([ADR 0004](https://github.com/Blazheiko/vibe-template/blob/main/docs/adr/0004-result-for-expected-outcomes.md)). 1) For a recovery code, the cleanup, on every request that gets this far (the one that activated and a repeat that finds the sign-in `already`), before its success answer: it closes the sockets of the **rotated** token only (except those of the new session) — a session signed in with the new token between two attempts keeps its sockets, connections still being opened are marked by the same token — and destroys the sessions of the rotated token, except the browser's own session even when it carries that token (step 3 deletes it under the lock). It is idempotent; when it fails (Redis, a deletion stopped part-way) the answer is 503 `mfa_completion_pending` and the repeat runs it again. 2) The claim of the at-most-once effects of the sign-in (the new sign-in mail, the "User logged in (MFA)" log line, the session-list event, and for a recovery code the `recovery_code_used` notice): the activation marks the ticket `effects: 'pending'`, and a one-shot Lua claim (`pending` → `done`) gives them to exactly one request — the one that activated, or the repeat after a 503 — which runs them right away. A claim that fails on Redis answers 503 `mfa_completion_pending` and leaves the effects `pending` for the repeat; a claim that ran but whose answer was lost leaves `done`, so the repeat sends nothing twice (those effects are skipped then, never run twice). 3) The deletion of the browser's previous signed-in session, under its own user's row lock ([Р13](/en/backend/auth#credential-changes-from-a-session)), last: when the lock cannot be taken nothing is deleted, the answer is 503 `mfa_completion_pending`, and the repeat finds the sign-in `already`, the effects `done` (they ran once already), deletes the record and signs in. After the deletion the session-list event of the replaced session's user is sent again: the one sent with the effects could still show it. 4) The new session's cookie: a 503 answer does not carry it, so the ticket is not deleted before the repeat finishes the sign-in. The ticket still exists then: only a request that already comes with the new session deletes it, and that session's cookie comes with the success answer. It deletes only the ticket of its own completion (`completionId`) and only then clears the ticket cookie (or when no ticket is left); a ticket of another completion — a newer second step of this browser while the older session still sends requests — stays with its cookie, as on a Redis failure.
- An attempt holds a reservation of the ticket (`MFA_RESERVATION_TTL_SECONDS`), checked with the clock of the capture itself: a factor check or a row lock that outlasted it rolls the proof back and answers 401 `mfa_attempt_expired` (the TOTP step, the recovery code and the passkey counter stay unspent). While a confirmed attempt finishes, `POST /auth/mfa/webauthn/options` answers 503 `mfa_completion_pending` too: the browser repeats the same verify request, not a new ceremony. The check only reads the second step's challenge; the failure count or the capture of the ticket spends it, atomically with them and only while it is still the challenge the answer was checked with. A passkey answer whose challenge is gone, spent or replaced by new options is not a wrong proof: 401 `mfa_attempt_expired`, no failure counted, and the browser runs a new ceremony. An attempt that rolled back before the capture (a lapsed reservation, for one) spends no challenge: the same answer, like the same TOTP code, may sign in again.
- `{ method: 'continue' }` carries no proof: it only finishes a sign-in this browser's ticket already confirmed (a ticket in the `completing` or `activated` state, the ticket cookie and its binding cookie `mfa_bind`), when the answer was lost or the page reloaded and the form has no request to repeat. The form sends it when `POST /auth/mfa/webauthn/options` answers `mfa_completion_pending`, with the same pauses. `activated` is activated with the same session; `completing` is read with `pg_xact_status`: committed signs in, rolled back opens the ticket again and answers 401 `mfa_attempt_expired` (the browser gives a new proof), unknown answers 503 `mfa_completion_pending`. For an `open` ticket `continue` proves nothing: 401 `mfa_attempt_expired`, with no reservation and no failure counted. The ticket of another browser answers 401 `mfa_ticket_invalid`. The route's rate limit bounds it like the other verify requests; it does not spend the user's code budget (`AUTH_MFA_VERIFY_MAX_ATTEMPTS_PER_USER`), as the repeat of a confirmed request does not, since no proof is checked. While a sign-in finishes, the form hides the switches to other factors. The form keeps every verify request, `continue` too, as pending **before** sending it and drops it only on a final answer (success, a refusal with a reason or any other `4xx`): a request whose answer the network lost (or a `5xx`) is sent again by "Try again", not replaced by asking for the factor. A `429` (the rate limit) and a `408` are not final either: the request is kept, the form shows the rate-limit message, and "Try again" sends the same request without asking for the factor again.
- The form keeps the second step of a password sign-in in memory. After a reload the sign-in page asks `POST /api/auth/mfa/state` before a new sign-in: for a ticket of this browser (the ticket cookie and the binding, as `continue` checks them) it answers `{ status: 'mfa_required', methods }` with the account's methods, as at sign-in, plus `completing: true` once an attempt was confirmed; then the page shows the second step again, and for `completing` the form sends `continue` at once. No cookie, an expired ticket, the ticket of another browser or an account left without factors answer `{ status: 'none' }` and nothing more. The request reserves, counts and changes nothing.
- The success answer of `POST /auth/mfa/verify` (every method, `continue` too) carries `recovery: { expiresAt, replaced }` when the created session is a recovery session (the same state `main/init` gives) and nothing for an ordinary sign-in. The client stores it before it opens the account page, so that page never asks a route a recovery session is refused.
- A new social sign-in linked to an account with MFA is stored only after the TOTP second step; a recovery-code sign-in does not store it.

**What is guaranteed for the last recovery code.** The ticket lives in Redis. A failed activation, a briefly unreachable Redis and a lost answer do not lose the code. Losing the whole Redis together with the ticket (or the database or Redis being down for the whole 5 minutes of the ticket) after the commit leaves the code spent without a session; an administrator helps then. So Redis in production should persist (AOF).

## Passkeys

The library is [`@simplewebauthn`](https://simplewebauthn.dev/) (`server` in the backend, `browser` in the frontend, exact versions). One function, [`verifyWebAuthnCeremony`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/auth/mfa/webauthn-ceremony.ts), checks every browser answer the same way for registration, passwordless sign-in, the second step and step-up (an architecture test keeps the library calls there):

- user verification (UV) required: a fingerprint, a face or the device PIN;
- the exact `origin` of the `WEBAUTHN_ORIGINS` list and the exact `WEBAUTHN_RP_ID`;
- a challenge of its purpose and binding: `register:<sessionId>`, `login`, `mfa:<ticket hash>`, `reauth:<sessionId>`; one-time (`GETDEL` in Redis, an atomic consume of the session data, and for `mfa:<ticket hash>` a spend in Lua together with the failure count or the capture of the ticket);
- the key belongs to the expected user; in a passwordless sign-in the answer's `userHandle` equals the owner's random `users.webauthn_user_handle` (not the id, not the email);
- the signature counter: `0` on both sides is fine (synced passkeys), otherwise it only grows (a conditional `UPDATE`). A regression is refused and recorded as `auth.passkey.counter_regressed`; the key stays, the owner decides.

**Registration.** `POST /account/passkeys/options` (rows 1–2 of the matrix; the first factor needs a verified contact, 409 `recovery_contact_required`) puts the challenge and an `enrollmentId` into the session data. `POST /account/passkeys` checks the answer and stores the key; a repeat after the commit returns the same key, and another key for a finished registration is 409 `enrollment_used`. A first passkey issues the recovery codes. Before a new key is written (and a new TOTP in `POST /account/mfa/totp/confirm`), under the user's row lock, the proof the first step kept is checked again against the current factors (`isProofAdmissible`, [`proof-policy.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/mfa/proof-policy.ts)): when another session turned MFA on meanwhile, a password or a recent OAuth sign-in no longer allows adding a factor, and the answer is the 403 of the matrix (`reauth_required`, `recovery_session` for a recovery session that ended). The proof's freshness is not checked again, and the audit records the kept proof (Р14). A repeat of an already committed enrollment still finishes its session write. At most 20 keys (409 `passkey_limit`), attestation `none`, `residentKey: required`. Removal (row 3), under the user's row lock, never leaves the account without a way to sign in (409 `last_sign_in_method`).

**A passkey-only sign-in** is a full level-2 sign-in (`amr: ['webauthn']`) with no second step. An unknown key, a bad signature and a foreign `userHandle` answer the same 401. The sign-in page also offers the passkey in the autofill of the identifier field (conditional UI, `autocomplete="username webauthn"`).

::: warning The RP ID does not change
A passkey is bound to its RP ID for good. Changing `WEBAUTHN_RP_ID` after the launch makes every registered passkey unusable (the password, TOTP and the codes stay). That is why a production-like environment names it explicitly instead of deriving it from a URL.
:::

## Step-up

The session keeps `auth`: the level of the sign-in (`aal` 1 or 2, never raised), the sign-in methods (`amr`) and when each method was last proven. An action of the matrix asks whether the needed proof is fresh (`AUTH_REAUTH_WINDOW_SECONDS`, 300 s by default) and answers `403 { reason: 'reauth_required', details: { kind: 'reauth_required', proofs } }`; the client shows a dialog with just those proofs and repeats the request.

| Action                                     | Without MFA                                                  | With MFA                |
| ------------------------------------------ | ------------------------------------------------------------ | ----------------------- |
| Turn on the first factor                   | a fresh password (or a social sign-in ≤ 10 min, no password) | —                       |
| Add / replace a factor                     | —                                                            | a fresh TOTP or passkey |
| Turn a factor off, new codes               | —                                                            | a fresh TOTP or passkey |
| Change the password, link a phone or email | a fresh password (or a recent social sign-in)                | a fresh TOTP or passkey |
| Remove a social sign-in                    | the same                                                     | a fresh TOTP or passkey |
| End other sessions                         | the session only                                             | the session only        |

For an account with MFA the password alone confirms nothing. Linking a phone or an email is confirmed at its start; the SMS code or the link finish it without another step-up, but any change of the MFA state voids the links still pending.

The first factor needs a verified email (or a phone with `AUTH_PHONE_ENABLED`): through it the user sets a password again after losing access.

## Recovery

- An ordinary password reset does **not** turn MFA off. The owner of an unverified address taking the account over (`claimLocked`) removes the factors with everything else set up before the proof.
- A recovery code (16 characters, 80 bits, one-time) opens a **recovery session**: level 1, an absolute lifetime `MFA_RECOVERY_WINDOW_SECONDS` (900 s by default), no WebSocket (`main/init` answers `wsToken: null`). The other sessions end. Only `main/init`, the `/account/mfa/*` routes, `recovery/finish` and `logout` are allowed; everything else answers `403 recovery_session`. After such a sign-in the frontend opens `/account` at once, even when the sign-in page had a `?redirect=`. Removing the old factor or new codes come only after the factor was replaced. After finishing, an ordinary sign-in with the new factor.

## Staff

With `MFA_REQUIRED_FOR_STAFF=true` (the default) a staff role (any role with permissions) works only with a second factor. One policy, [`staffMfaPolicy`](https://github.com/Blazheiko/vibe-template/blob/main/packages/shared/src/mfa/staff-mfa-policy.ts) (mode `MFA_STAFF_FACTOR=any`: TOTP or a passkey), answers three questions, and every consumer asks it ([`staff-policy.ts`](https://github.com/Blazheiko/vibe-template/blob/main/packages/backend/src/app/services/auth/mfa/staff-policy.ts)):

- **Giving a role** (the admin area and the CLI `user:set-role`): only to an account with a factor, otherwise `409 mfa_not_enrolled`. A first administrator made by the CLI sets up TOTP as an ordinary user first; the `db:seed` demo admin gets TOTP from `SEED_ADMIN_TOTP_SECRET`.
- **`can:` and `ws_can:`**: a level-2 session with a fresh (`MFA_STAFF_FACTOR_MAX_AGE_HOURS`, 12 h by default) factor proof, not a recovery session. Otherwise `403 mfa_required` (no factor) or `403 mfa_session_required`; the frontend goes to `/account?section=security` with an explanation.
- **Confirming staff actions** (a role change, an MFA reset): a fresh factor; for an account without MFA, the password.

The admin WebSocket channel keeps its subscribers in the order of their deadline and **drops the expired ones synchronously before every publish**, so an event published at `t` never reaches a socket whose deadline is `≤ t`, whenever its timer runs. The timer sends `access_changed { reason: 'mfa_session_required' }` and an open admin page goes to the sign-in. A step-up updates the `auth` of the session's connections on every instance (the bus event `session_auth_changed`).

**An MFA reset by an administrator**: `POST /api/admin/users/:id/mfa/reset { reason }` (`can:users.mfa.reset`, the admin's alone) or the CLI `pnpm --filter backend user:mfa-reset --email <email> --reason "<why>"` (`make user-mfa-reset`), the emergency exit of the last administrator. Not one's own account (`403`: the recovery codes or the CLI). Before the write, under the row locks (in ascending id), the actor is checked again: its session token is still the same and the record of the request's session is still stored (ending that one session from the session list, a plain logout of it and a new sign-in in the same browser that replaces it delete the record under the same row lock; else `401 session_revoked`; a logout that could not get the lock answers `503 logout_retry` and deletes nothing, see [Authentication](/en/backend/auth#credential-changes-from-a-session)), it still holds the permission (else `403`), its proof is fresh; a role change does the same. An account that would be left without a way to sign in (only a passkey) gets `409 last_sign_in_method` without exception: the user sets a password through "forgot password" first. TOTP, the passkeys and the codes go, `session_token` rotates (the sessions and sockets end), the event `auth.mfa.reset` records the reason, the owner gets a notification and a mail.

**The `passkey` mode** (`MFA_STAFF_FACTOR=passkey`, recommended): staff need a passkey, and the session a sign-in or step-up by a passkey (`webauthn` among its methods, a fresh `verified.webauthn`); TOTP stays a second factor for the account's ordinary actions but does not open the admin area. The server refuses to start in this mode without a configured WebAuthn. Removing a factor of a staff account that leaves it outside the mode is `409 mfa_required_for_role` (in `any`, the last factor; in `passkey`, the last passkey even with TOTP left; a TOTP-only account turns TOTP off after adding a passkey); the admin's reset is the exception. `GET /api/account/mfa` tells the client `staffFactor`, and staff without a passkey see a banner.

**Switching to `passkey`:** configure `WEBAUTHN_RP_ID` and `WEBAUTHN_ORIGINS` → turn `MFA_REQUIRED_FOR_STAFF` on in the `any` mode → staff add passkeys (the banner says so) → switch `MFA_STAFF_FACTOR=passkey`. After the switch staff without a passkey get `mfa_required` until they register one, and sessions opened by TOTP get `mfa_session_required`.

::: warning Transitional risk
Staff accounts without a factor that existed before the switch-on, and the `db:seed` admin in a production-like environment (without `SEED_ADMIN_TOTP_SECRET`), get `mfa_required` in the admin area until they set up a factor (row 1 of the matrix: a fresh password). Until then whoever knows such an account's password can set up its first factor. Set the staff factors up right after the upgrade.
:::

## Configuration

| Variable                                | Default                      | What it sets                                                                                                        |
| --------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------------------------------- |
| `MFA_ENCRYPTION_KEYS`                   | —                            | `<keyId>:<base64 of 32 bytes>[,…]`; required in production-like                                                     |
| `AUTH_REAUTH_WINDOW_SECONDS`            | `300`                        | how long a step-up counts                                                                                           |
| `MFA_RECOVERY_WINDOW_SECONDS`           | `900`                        | the lifetime of a recovery session                                                                                  |
| `MFA_TICKET_TTL_SECONDS`                | `300`                        | the lifetime of a second-step ticket                                                                                |
| `MFA_RESERVATION_TTL_SECONDS`           | `30`                         | how long an attempt holds its place in the ticket                                                                   |
| `AUTH_MFA_VERIFY_MAX_ATTEMPTS_PER_USER` | `10`                         | second-step and step-up codes per user per window                                                                   |
| `AUTH_MFA_VERIFY_WINDOW_SECONDS`        | `900`                        | the window of that limit                                                                                            |
| `OAUTH_FRONTEND_MFA_URL`                | `/login?mfa=required`        | where OAuth sends an account with a second factor                                                                   |
| `MFA_REQUIRED_FOR_STAFF`                | `true`                       | a staff role works only with a second factor and a fresh proof of it                                                |
| `MFA_STAFF_FACTOR`                      | `any`                        | the staff factor: `any` (TOTP or a passkey) or `passkey` (recommended)                                              |
| `MFA_STAFF_FACTOR_MAX_AGE_HOURS`        | `12`                         | how long a factor proof counts for staff                                                                            |
| `WEBAUTHN_RP_ID`                        | the host of `FRONTEND_URL`   | the RP ID of the passkeys; required in production-like, never changed after the launch                              |
| `WEBAUTHN_RP_NAME`                      | `APP_NAME`                   | the name in the passkey dialog                                                                                      |
| `WEBAUTHN_ORIGINS`                      | the origin of `FRONTEND_URL` | the exact origins of the ceremonies, comma-separated (`https://` in production-like), each on the RP ID or below it |

The TOTP secret is stored encrypted (AES-256-GCM, the owner as associated data). The first key of the list encrypts, the others read, so keys rotate without re-encrypting everything. Without `MFA_ENCRYPTION_KEYS` outside production a key is derived from `APP_KEY` (with a warning in the log). Losing every key makes every TOTP factor unusable.

## Audit log and notifications

The events `auth.mfa.totp.enabled|replaced|disabled`, `auth.mfa.recovery_codes.regenerated`, `auth.mfa.recovery_code.used`, `auth.passkey.added|removed|counter_regressed`, `auth.mfa.reset` go to the [audit log](./audit-log) with their proof (`metadata.proof`). Every change of the factors sends a security notification and a mail to the account's address.
